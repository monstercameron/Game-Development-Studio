# Resilience: crashes, power loss and recovery

This guide records what happens to every piece of durable Forge state when the studio, a worker, an engine or the computer stops without warning, what was changed to make that safe, and what is still unsafe. It describes **observed behaviour from reading the code and running the tests in `test/`**. Failure drills on a real installation (real GPU engines, a real power cut, Windows shutdown) were not run; the [manual drills](#manual-drills) at the end say how to run them and what to expect.

## Guarantees and non-guarantees

Forge guarantees, within the limits of the storage hardware honouring flush requests:

- **A committed queue change is not lost.** `jobs.sqlite` and the other irreplaceable databases use SQLite WAL (or the rollback journal) with `synchronous=FULL`. A power loss can lose a transaction that had not committed; it cannot lose or corrupt one that had.
- **A final file name never holds a partial file written by current code.** Every writer stages a hidden file in the same directory, flushes it (`fsync`), and only then renames or links it into place ([durable-file.js](../runtime/durable-file.js)). A crash leaves a hidden `.tmp`/`.part` file, never a half-written asset under its real name.
- **A job whose remote outcome is unknown is never resubmitted automatically.** A render that may have reached an engine becomes `interrupted` with the reason, and stays that way until a person resolves it.
- **A damaged database is never deleted.** It is moved aside as `<name>.corrupt-<timestamp>`, the newest backup that passes its own integrity check is restored, and only when there is none does the database start empty, with an error entry in the Recovery report.
- **Engines are not stopped to recover.** Engines run detached from the studio. After a studio restart Forge reconnects to the ones it can prove it owns and leaves everything else alone.
- **The studio says when it restarted after an unclean exit.** The absence of the clean-shutdown marker produces a Recovery report that names what was interrupted, repaired and still needs a decision.

Forge does **not** guarantee:

- **Durability on hardware that lies about flushes** (some USB bridges, RAID caches without battery backup, consumer SSDs under power loss). `fsync` is a request.
- **Directory flushes on Windows.** Windows cannot open a directory for `fsync`; Forge relies on NTFS journaling the rename and flushes the file data before it. The helper reports `false` there and carries on.
- **Output written by versions before this change.** Files saved earlier by the old writer could, after a power loss, be zero-filled or short under their real name. New code does not create them; it cannot find them in general. The finalizing recovery below only trusts files whose size and signature prove them whole.
- **Resuming a render that an engine lost.** If an engine restarted and forgot a job, the job stays `interrupted` for a person to decide. Diffusion, TRELLIS and other model runs have no cheap checkpoints and cannot continue half-way; TRELLIS cascade stages in particular restart from the beginning.
- **Detecting an engine that dies without closing its port** in under the 1.5 second health timeout, or telling a stuck GPU kernel from a slow render.
- **Logs.** `logs.sqlite` and the log spool belong to the logging subsystem; they are diagnostic, rebuildable and not part of the backups here.

## How recovery works

1. **Startup marker.** The parent process (`server.js`) writes `.forge-runtime/session-state.json` as `running` and refreshes a heartbeat every 30 seconds. An orderly stop rewrites it as `clean`. A stop that missed its deadline writes `forced`. At the next start, `running` or `forced` means the previous session ended abnormally: Forge records a `session.unclean_exit` event, sets `FORGE_PREVIOUS_UNCLEAN=1` for the host and its children, and keeps the previous session's last-alive time for the report. See [studio-lifecycle.js](../runtime/studio-lifecycle.js) and [session-state.js](../runtime/session-state.js).
2. **Recovery journal.** Any process appends a line to `.forge-runtime/recovery-events.jsonl` (codes, ids, counts; never prompts or paths). The report reads the lines written since the previous session began. The same events are also logged through the structured log as `recovery.*`.
3. **Database open policy.** Every Forge database opens through [durable-db.js](../runtime/durable-db.js): explicit pragmas, a once-per-process `PRAGMA quick_check`, and the quarantine/restore response above.
4. **Queue takeover.** When a queue process takes over the lease from a dead owner (a new lease epoch), `submitting` jobs become `interrupted` and `preparing` jobs go back to `waiting_engine`. `running` and `finalizing` jobs with a remote ID keep their state and their ID, and are polled again.
5. **Startup sweep.** [recovery-sweep.js](../runtime/recovery-sweep.js) finds hidden staging files. It deletes a `.tmp`/`.part` file only when it is older than 24 hours and no open job's ID appears in its name; everything else is reported, never removed.
6. **Recovery report.** `GET /api/recovery`, the Recovery panel at the top of the studio, and the read-only MCP tool `forge_recovery_report`. The report is computed from evidence when it is read, so a job resolved in the panel disappears from it. A snapshot of the startup state is also kept in `.forge-runtime/recovery-report.json`.
7. **Backups.** Every 15 minutes (first run one minute after start) the studio copies `jobs.sqlite`, each project's `.forge-meta.sqlite`, `settings.sqlite`, `i18n.sqlite`, `credentials/keys.sqlite` and `megascans.sqlite` into `.forge-runtime/backups/`, if they changed ([backup-manager.js](../runtime/backup-manager.js)).

### The Recovery report

| Section               | Meaning                                                                                                                                                                                                                                      |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `unclean`, `previous` | Whether the previous session ended without an orderly stop, when it was last known alive, and the stop reason if there was one.                                                                                                              |
| `recoveryNeeded`      | A supervisor stopped restarting a process that crashed repeatedly (the host or the runtime worker).                                                                                                                                          |
| `jobs`                | Jobs in `interrupted` or `needs_attention`, each with a kind (`unknown_outcome`, `needs_attention`), whether it has a remote ID, whether it is **provably safe to retry**, and whether a finished output file already exists in the project. |
| `orphans`             | Hidden staging files, conflict markers, damaged databases set aside, conversion folders and project folders without readable metadata; plus how many stale staging files were removed.                                                       |
| `databases`           | `ok`, `restored` (from a backup, changes after it were lost), `started_fresh` (no backup) or `quarantined` for each database, with the number of backups.                                                                                    |
| `engines`             | Engines that are unreachable or have an ownership state: `reason: 'refused'` means nothing was listening, `'timeout'` means a process accepted the connection and did not answer (a hang). `null` means the runtime could not be asked.      |
| `events`              | The recovery journal lines for this report.                                                                                                                                                                                                  |

Actions are `POST /api/recovery` with `Origin` equal to the studio origin and `X-Forge-Request: recovery`, like `/api/errors`:

| Action                                                 | What it does                                                                                                                                                      |
| ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dismiss`                                              | Hides the report until something new needs attention (a fingerprint of the shown problems is stored).                                                             |
| `rescan`                                               | Repeats the staging scan without deleting anything.                                                                                                               |
| `resolve-job` (`confirm: 'engine-job-not-running'`)    | Marks an **interrupted** job cancelled through the normal queue `resolve` operation, after the user confirms the engine is not rendering it.                      |
| `retry-job`                                            | Queues a job again only if it is provably safe: preparation stopped before submission, a refusal before acceptance, or a vegetation job. Otherwise `409`.         |
| `quarantine-orphans` (`confirm: 'quarantine-orphans'`) | Moves reported files into `.forge-runtime/quarantine/<timestamp>/` (recoverable). File paths are never taken from the request; ids are looked up in a fresh scan. |

## Failure mode matrix

| Failure                                            | What happens now                                                                                                                                                                                                                                                                                                                                   | Result                                                                                                                                                                  |
| -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Studio host crash** (`kill -9` of the HTTP host) | `host-supervisor.js` restarts it with exponential backoff (250 ms to 10 s). The runtime worker (child of the host) stops; the parent keeps the engine handles. After 5 crashes in 10 minutes it **stops restarting** and the studio port answers `503` "Recovery needed" ([recovery-needed-server.js](../runtime/recovery-needed-server.js)).      | Queue state is in `jobs.sqlite`. The new queue takes over the lease: `submitting` becomes `interrupted`, the rest continues. Recovery events `supervisor.host_crashed`. |
| **Parent (`server.js`) crash or kill**             | Everything under it stops except the detached engines. The session marker stays `running`.                                                                                                                                                                                                                                                         | Next start: unclean report. Recoverable engines are adopted; others are not (see below).                                                                                |
| **Runtime worker crash**                           | `supervisor.js` restarts it (backoff). After 5 crashes in 10 minutes it stops, `/api/runtime/health` shows `crashLooped`, and a `recovery-needed.json` marker is written.                                                                                                                                                                          | Same lease takeover as above. Pending HTTP requests fail with "retry the request".                                                                                      |
| **Forked job process crash**                       | The queue notices the exit. A `submitting` job becomes `interrupted` (unknown outcome). A job with a remote ID goes back to `running` and a new worker re-polls the engine. A vegetation worker death fails the job with a retry message.                                                                                                          | No duplicate submission.                                                                                                                                                |
| **Engine crash mid-job**                           | The job process gets a 404 or connection errors. Connection errors retry every 5 seconds ("Waiting to reconnect"). A 404 means the engine no longer knows the job: the job becomes `interrupted`. The engine manager restarts a crashed engine up to 3 times (reset after 30 seconds of uptime), then records `supervisor.engine_crash_loop`.      | The job is interrupted, not resubmitted. The Recovery report lists it as `unknown_outcome`.                                                                             |
| **Engine hang**                                    | The 1.5 second health check times out. `inspectService` now reports `reason: 'timeout'` (a process answered the connection but not the request) versus `reason: 'refused'` (nothing listening).                                                                                                                                                    | Visible in the report and `/api/runtime/services`. Forge does not kill a hung engine on its own; use Models & services (offload / force stop, both confirmed).          |
| **Out of memory or commit exhaustion**             | Windows ends a process. For a job process or an engine this is the crash cases above; for the host or worker it is the crash cases above. Model admission (`model-load.js`) still checks commit and GPU memory separately before a load.                                                                                                           | No special handling beyond the crash cases.                                                                                                                             |
| **Disk full**                                      | Output writes fail before the final name exists (`ENOSPC` while writing the temp file), so no partial asset appears; the job fails with the error. SQLite commit failures roll back. Megascans imports pre-check free space.                                                                                                                       | Recoverable by freeing space and retrying. Not tested with a real full disk.                                                                                            |
| **Power loss mid SQLite write**                    | WAL frames after the last commit are ignored; committed transactions are intact (`synchronous=FULL`). A torn write elsewhere is caught by `quick_check` at the next open.                                                                                                                                                                          | Tested with a killed writer, a torn WAL tail and a zeroed page ([durable-db.test.js](../test/durable-db.test.js)).                                                      |
| **Power loss mid file write**                      | Final names are never partial for current writers. Hidden `.tmp`/`.part` leftovers are swept after 24 hours when unreferenced. Old files may still be partial.                                                                                                                                                                                     | See the matrix above.                                                                                                                                                   |
| **Reboot**                                         | Same as power loss unless Windows shut down cleanly (see below). Engines do not survive a reboot; the queue reconnects, finds no engine, and `recoverService` restarts Forge-owned recoverable engines when `engines.autoStart.*` allows it. A job with a remote ID whose engine restarted becomes `interrupted` (the engine returns 404).         | Needs a decision per interrupted job.                                                                                                                                   |
| **Sleep / resume**                                 | A wall-clock gap of more than 30 seconds beyond the 5 second timer period in the runtime worker is treated as a resume. A job still in `submitting` becomes `interrupted` (unknown outcome) and its worker is killed. Jobs that already have a remote ID are untouched: their pollers reconnect on their own. The browser reconnects with backoff. | Event `power.resumed`. Engines usually survive sleep; if one did not, the next poll shows `refused`.                                                                    |
| **User closes the window / tray "Quit"**           | The desktop window hides; quitting it does not stop the studio. Tray "Stop Studio..." runs `stop-server.ps1`, which now writes a stop request and waits 8 seconds for an orderly stop before terminating the process.                                                                                                                              | Orderly stop writes the clean marker.                                                                                                                                   |
| **Windows shutdown or logoff**                     | The tray handles `SessionEnding`: it writes a stop request and waits up to 4 seconds for the studio to exit. The parent polls for the request once per second and runs the same orderly stop with a 6 second deadline; after that it exits and marks the stop `forced`.                                                                            | **Not verified on a real shutdown**; see the drill. Console `SIGINT`/`SIGTERM`/`SIGBREAK`/`SIGHUP` also start the orderly stop.                                         |
| **Crash during a chain**                           | Chain parents and children are separate job rows. The parent keeps its state (interrupted parents hold the queue head). A child whose parent failed fails on the next tick with the existing "depends on failed" message; a child whose parent was cancelled is cancelled.                                                                         | Tested ([job-crash-recovery.test.js](../test/job-crash-recovery.test.js)).                                                                                              |
| **Crash during model load / offload**              | The `checking`/`loading` barrier persists. At takeover `checking` becomes `loading`; the load monitor checks the service before releasing it.                                                                                                                                                                                                      | A timeout never clears the barrier.                                                                                                                                     |
| **Crash during model download / staging**          | The Hugging Face CLI resumes from its `.incomplete` files when the same command is run again. Installer staging folders are new folders; nothing existing is changed.                                                                                                                                                                              |                                                                                                                                                                         |
| **Crash during a Megascans download**              | The `.part` file stays; the import is `interrupted`; Retry asks Fab for a fresh signed address and resumes with a Range request (repeating the tail after an unclean exit).                                                                                                                                                                        |                                                                                                                                                                         |
| **Crash during ZIP extraction**                    | Extraction goes into a work folder inside the import's staging folder, which is removed. Nothing reaches the project until the work folder is renamed whole.                                                                                                                                                                                       | Extracted files are flushed first.                                                                                                                                      |
| **Crash during project move / trash / restore**    | There is no project move. Asset trash writes the manifest atomically before moving the asset; restore stages and links a copy, then removes the trash copy: a crash leaves both copies, never neither.                                                                                                                                             | Tested ([coverage-trash.test.js](../test/coverage-trash.test.js)).                                                                                                      |
| **Crash during asset conversion**                  | The converter writes to a hidden `.forge-convert-<id>` file or folder and links the result out of it after flushing.                                                                                                                                                                                                                               | A leftover folder is reported (`conversion_staging_folder`) and can be moved to quarantine.                                                                             |
| **Crash during an export**                         | Exports are browser downloads of existing files (`GET`); the studio writes nothing to disk for them.                                                                                                                                                                                                                                               | No server-side state.                                                                                                                                                   |

### Engine recovery

Engines are launched detached, so they survive the studio. After a restart Forge can re-adopt an engine only with its ownership journal entry plus a successful identity challenge (control token, per-start nonce, OS listener PID, executable path, process creation time).

| Engine                                                                                                                                | Re-adopted after a studio restart                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Qwen Image (`images`), game logic, voices (`tts`), Hunyuan3D, TRELLIS.2, SAM 3.1, HY-Motion, MotionBricks, speech recognition (`asr`) | Yes (existing).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| **Video (H3)**                                                                                                                        | **Yes, new.** The guard (`runtime/h3_guard.py`) is the same architecture as the speech guard: the listener on the studio port is the guard process, started with a per-start control token. It now answers `GET /api/forge/identity` with the nonce, and `engines.js` lists `video` among the recoverable guards. Previously the video engine had no way to prove its identity. **Not exercised against a real video render** (no GPU); the identity endpoint is covered by `test/h3-guard-identity.test.js` against the real guard with a substitute H3 server. |
| Music (YuE2), sound effects, world, chat (llama.cpp)                                                                                  | No. They have no identity endpoint. A surviving one is reported as a foreign process on its port and is neither adopted nor stopped. To make them recoverable each needs a guard like `h3_guard.py`; that is more than a small change and was not attempted.                                                                                                                                                                                                                                                                                                     |

A restarted engine that holds no record of a job answers `404`, which turns that job `interrupted`. Forge never infers that a job has stopped from a timeout.

## Job state machine after a crash

Tested in [job-crash-recovery.test.js](../test/job-crash-recovery.test.js) by building the crashed state (and, for the submission case, killing a real queue process) and taking over the lease.

| State at the crash                           | After takeover                                                                                                                                                                                                                                                                                                              | Resubmitted?                                | Notes                                                                                                                                           |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `queued`, `waiting_engine`, `waiting_memory` | unchanged                                                                                                                                                                                                                                                                                                                   | no (never reached an engine)                | Order and manual reordering (`queue_rank`) are preserved.                                                                                       |
| `preparing`                                  | `waiting_engine`, stage "Rechecking the engine after a runtime restart."                                                                                                                                                                                                                                                    | no                                          | Preparation never submits. Admission and engine start run again.                                                                                |
| `submitting`                                 | `interrupted`, reason "Submission may have reached the engine..."                                                                                                                                                                                                                                                           | **never**                                   | The remote outcome is unknown. Needs `resolve` (cancel) after checking the engine. The report marks it `unknown_outcome` and not safe to retry. |
| `running` with a remote ID                   | unchanged                                                                                                                                                                                                                                                                                                                   | no (the ID is polled)                       | A new job process reconnects. If the engine forgot it (404) the job becomes `interrupted`.                                                      |
| `finalizing` with a remote ID                | If the project already holds `forge-<jobId>.<ext>` and its size and signature prove it whole (GLB length field, PNG end marker, WAV RIFF length, BVH frame count), the job becomes `completed` without starting an engine. A damaged file is left for `saveAsset` to download again. A missing file continues as `running`. | no                                          | Types with only a header check (FLAC, WebM, PLY) are not completed from a file alone.                                                           |
| `interrupted`                                | unchanged; blocks the queue head                                                                                                                                                                                                                                                                                            | no                                          | The Recovery panel offers "Mark as cancelled" after the user confirms the engine is not rendering it.                                           |
| `needs_attention`                            | unchanged; blocks the queue head                                                                                                                                                                                                                                                                                            | no                                          | Retry is offered only when the job has no remote ID.                                                                                            |
| Chain parent `running`                       | unchanged                                                                                                                                                                                                                                                                                                                   | no                                          |                                                                                                                                                 |
| Chain child waiting                          | unchanged (`queued`, stage "Waiting for ...")                                                                                                                                                                                                                                                                               | no                                          | Resolved on the first tick after the parent finishes.                                                                                           |
| Chain child with a failed parent             | `failed`, "The ... this render depends on failed"                                                                                                                                                                                                                                                                           | no                                          | Retrying the parent requeues the child.                                                                                                         |
| `vegetation` `running`                       | the worker's death fails the job with a retry message; a stranded row is grown again                                                                                                                                                                                                                                        | yes: deterministic, CPU only, no remote job | The only type that is safe to run again automatically.                                                                                          |

Types with checkpoints: none are resumable mid-run. TRELLIS cascade stages, diffusion steps, music and speech generation restart from the beginning. What does resume: Megascans downloads (Range, fresh signed address), model installs (the Hugging Face CLI), and finished-but-not-yet-recorded renders (the `finalizing` rule above).

## Procedures

### Reading the Recovery report

Open the studio. If the panel is not shown there is nothing to decide. Otherwise it says when the previous session was last alive and lists the items. You can also run `GET /api/recovery` or the MCP tool `forge_recovery_report`. Dismissing hides the current set; new problems bring it back.

### Handling an interrupted job

1. Open Models & services and the engine's own log. Is the engine rendering this job? If yes, wait.
2. If a saved output is listed, it is in the project already; the job does not need to run again.
3. Tick "I checked that the engine is not rendering this job" and choose **Mark as cancelled**. The job becomes `cancelled`; queue it again from its page if you still want the result.

### Restoring a database from a backup

Backups are in `.forge-runtime/backups/<name>/<name>-<timestamp>.sqlite` (`jobs`, `settings`, `i18n`, `keys`, `megascans`, and `projects/<folder>-<hash>/` for project metadata). They are complete, checked SQLite files.

1. Stop the studio (`stop-server.ps1`), so nothing holds the database open.
2. Move the damaged `jobs.sqlite` (and `jobs.sqlite-wal` / `-shm`) somewhere safe; do not delete them.
3. Copy the chosen backup to `.forge-runtime/jobs.sqlite`.
4. Start the studio. The integrity check runs, and the lease takeover treats every open job as above.

The studio does this automatically at startup if the check fails; the manual procedure is for choosing an older backup. `GET /api/recovery/backups` lists what exists.

### Orphaned files

The report lists them by project and project-relative path. Move them to quarantine from the panel, or inspect them by hand. Nothing is deleted except stale `.tmp`/`.part` staging files older than 24 hours that no open job names.

### The studio shows "Recovery needed"

The host crashed five times in ten minutes and was not restarted. Engines that were running still are. Run `node server.js` from a terminal to see the error, fix it, and start the studio again. After the restart the Recovery panel lists anything that needs a decision.

## Manual drills

None of these were run for this change; they need the real installation. Run them with a disposable project and a cheap job (a short sound effect, a small image). Do not run them while valuable renders are queued.

1. **Kill the host mid-job.** Queue a sound effect. While it runs: `Stop-Process -Id <host pid> -Force` (the host pid is `server.pid` in `/api/diagnostics`; the supervisor pid in `supervisorPid` must stay). Expect the supervisor to restart the host within a few seconds, the job to keep `running` and finish, and **no** Recovery panel (the session did not end).
2. **Kill the supervisor mid-job.** Same, but kill the `supervisorPid`. Start the studio again. Expect: Recovery panel with "ended without an orderly shutdown"; the running job continues if its engine was adopted (images, tts, 3D, ...) or is `interrupted` with the "may have reached the engine" reason if it was still `submitting`.
3. **Kill an engine mid-render.** Force-stop the engine process from Task Manager. Expect the job to become `interrupted` ("no longer recognizes this job" or after the reconnect wait), an `engine.exited` event, and the engine restarted up to three times if configured to auto-start.
4. **Kill during a SQLite transaction.** The automated equivalent is `test/durable-db.test.js` ("killed inside a write transaction"). On a real install, `Stop-Process -Force` of the supervisor during a burst of enqueues and check `PRAGMA quick_check` on the copy of `jobs.sqlite`: it must return `ok`.
5. **Pull the plug equivalent.** Hold a render, then hold the power button (or use a VM and power it off hard). On the next start the Recovery panel lists the session's last-alive time, interrupted jobs, any stale staging files (they are removed only after 24 hours), and no database should need repair. Check `.forge-runtime/recovery-report.json`.
6. **Windows shutdown.** With a queued render, choose Restart. Expect the next start to show a clean session (tray `SessionEnding` handled) or, if Windows ended the process first, an unclean one with `endReason: deadline` or none. Record which, so the 4 and 6 second deadlines can be tuned.
7. **Sleep.** With a render running, sleep for a minute and wake. Expect a `power.resumed` event, no change to `running` jobs, and a `submitting` job (if you slept at the instant of submission) to become `interrupted`.
8. **Corrupt a database.** With the studio stopped, overwrite the middle of a copy of `settings.sqlite` and start. Expect the file set aside as `settings.sqlite.corrupt-<stamp>`, a restored backup (or `started_fresh` if none yet) in the report.

## Known gaps and options not built

- **No "shut down the PC when the queue finishes".** Not built: it is irreversible from the user's side and would need an explicit per-use confirmation, a visible countdown and a cancel button, and could not safely be reachable from MCP. If it is added it must live in the UI only.
- **Keep-awake while renders are queued.** The existing toggle (`power.keepAwake`) is manual and not saved. A queue-driven policy ("awake only while renders are queued") needs the queue state in the host and a release on idle and on crash; the release on crash already holds (the Windows request dies with the helper process). It is not built.
- **Hibernate and shutdown behaviour.** Hibernate is treated like sleep: wall-clock gap, `power.resumed`, `submitting` jobs interrupted, `running` jobs re-polled. A hibernated machine that is then powered off is a power loss.
- **Music, sound, world and chat engines are not adopted** after a studio restart (see above).
- **`logs.sqlite` and the log spool** are not covered by the integrity/backup policy.
- **Old output files** are not retroactively verified.
- **A project whose `.forge-project.json` was lost** must be repaired by hand.
- **Single volume assumptions.** Staging next to the target (needed for atomic rename and hard links) means a project on a filesystem without hard links falls back to copy-then-rename for duplicates and refuses `saveAsset`'s link commit with a clear error.
