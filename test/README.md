# Tests and verification

Run commands from `C:\Users\mreca\Desktop\Game Development Studio`. Automated tests use temporary projects, substitute workers, or loopback services where practical; read a test before running it to understand what it starts. Existing external GPU engines and project files should not be stopped or altered for a test.

## JavaScript service and UI logic

```powershell
node --test 'test/*.test.js'
node node_modules\vite\bin\vite.js build
```

The suite covers queue persistence/recovery, lease fencing, model-load barriers, GPU-memory admission, worker protocols, project assets and trash, model inventory/removal, HTTP, and MCP. Tests that use fake engines establish protocol behavior; they do not prove real GPU generation or visual/audio quality. The build only checks bundling; it is not a visual accessibility or device-layout review.

To run a focused group, pass the filenames after `node --test`, for example `test/model-inventory.test.js`, `test/model-removal.test.js`, and `test/project-workflow-mcp.test.js`.

For World studio changes, `node --test test/world-queue.test.js test/world-mcp.test.js test/nav-queue-status.test.js` covers the queue adapter, MCP and page indicators using substitute services. The WorldGen LoRA and perspective-ray helpers and Windows memory guard also have Python unit tests; see [agent setup](../docs/AGENT_SETUP.md#4-validate-the-right-layer) for the commands and environment paths. These tests do not run full GPU inference.

## Reordering the render queue

`node --test test/queue-move.test.js test/queue-move-http.test.js test/queue-move-ui.test.js` covers `queue_rank` ordering and the move rules on temporary state with autoStart off: rank then creation order, appending new renders, legacy rows with a NULL rank (including a database created before the column), `next`/`top`/`end`/`before`/`after`/`up`/`down`, no-op moves, one-row writes and renumbering when a gap is exhausted, refusal of running, preparing, interrupted, needs-attention, failed, cancelled, finished and engine-job renders, the chained-render clamp and carry (including a chain of three), stale `expectedRank` and a lost race with a second connection (409 with the fresh order, full rollback), persistence across a restart, the `queue_move` log record, the forecast order and strict request validation. `queue-move-http.test.js` runs the scheduler against a substitute sound engine on loopback (the moved render is claimed next, a running render cannot move), the real runtime worker behind the real route in an isolated runtime folder (head render blocked by a needs-attention job, every engine URL on a closed port) for validation, origin and `X-Forge-Request` checks and 409 bodies, and the MCP `forge_move_job` schema and request. `queue-move-ui.test.js` drives the queue page in jsdom against a fake runtime that applies the real planner: position badges, labelled controls and disabled reasons, optimistic update with forecast, rollback and error, conflict, keyboard pick-up/move/drop/cancel with the live-region text, and pointer dragging with the drop line and Escape. No engine, model or GPU is used. They do not check real drag behaviour on a touch screen or a screen reader's speech.

## Megascans cache, library, downloads and import queue

`node --test test/megascans-fab.test.js test/megascans-cache.test.js test/megascans-download.test.js test/megascans-import.test.js test/megascans-queue.test.js test/megascans-service.test.js test/megascans-mcp.test.js test/megascans-ui.test.js` covers the Megascans page without any network access to fab.com. A fake Fab and a fake delivery network on loopback (`test/fixtures/fake-fab.js`) stand in for the listing, detail, file-list, `download-info`, thumbnail and file endpoints, including 429 with `Retry-After`, 5xx, challenges, HTML where JSON is expected, redirects, ETags with 304, `Range` support, expired and wrong-host addresses, short and oversized bodies. The tests check the honest `Forge-Studio` User-Agent and the absence of cookies or other identity headers, one request in flight with a quiet interval, retry and backoff, the block and rate-limit pauses (no request while paused), refresh cooldown and the 24 h and 7 day TTLs, FTS5 search, a capped, resumable, cancellable scan that survives a simulated crash, single-flight sharing of identical requests, `If-None-Match` revalidation, serving everything from the cache when Fab is unreachable, and that a signed download address is never written to SQLite, logs or error messages. The download tests cover the license-confirmation gate (nothing is requested from Fab until a person ticks it), file grouping and the recommended file, the CDN host and HTTPS allow-list, size checks, resume with a Range request and a restart when the server ignores it, cancel and cleanup, the large-file confirmation and that no more than two downloads run at once. The import tests cover the strict ZIP reader and archive policy (zip-slip, absolute and drive paths, alternate data streams, reserved names, symbolic links, encryption, ZIP64, executables, duplicate names, size and ratio limits, CRC and understated sizes), safe extraction and atomic placement in a temporary project, the durable queue (the two-transfer cap under racing claimers in separate SQLite connections, restart recovery to `interrupted`, cancel, retry, dismiss, late results) and provenance in the asset details. The UI tests run the page in jsdom: search, filters, error, empty and blocked states, chunked loading with Load more, focus and the live region, the end-of-list observer, Read more from Fab only after scrolling, preview placeholder and failure states, the Licences and terms links (hrefs, `rel`, new-tab text), the confirmation checkbox, per-file Download buttons, progress bars with `aria-valuenow` and file validation. Archives are built in memory by `test/fixtures/zip-builder.js`; `test/fixtures/load-jsx.js` compiles components for jsdom. No test uses a model engine or the GPU. They do not exercise the real fab.com, a real browser upload of a multi-gigabyte file, or the 3D viewer. The one-off live checks against fab.com are described in [Megascans](../docs/MEGASCANS.md#verification-status).

## Native TRELLIS component suite

```powershell
cmd /c runtime\trellis-native-tests.cmd
```

This uses the current Visual Studio ARM64 and CUDA environment and checks CuMesh, FlexGEMM, O-Voxel, nvdiffrast, OpenCV preprocessing, sparse SDPA, and native imports. The CUDA component checks operate on small inputs; they do not load a full TRELLIS.2 checkpoint or generate a mesh. `runtime/trellis-native-probe.cmd` and `runtime/trellis-triton-probe.cmd` separately exercise a native CUDA kernel and a Triton GPU kernel.

## Real model checks

The following tests can load gigabytes of local weights and use the GPU. Check current free **system and GPU** memory and other running work before executing them. These checks use the installed Windows ARM64 Python environment and model files; they are not necessary for a docs-only change.

```powershell
& '.\.forge-runtime\trellis2-venv\Scripts\python.exe' '.\test\trellis_dinov3_cuda_test.py'
& '.\.forge-runtime\trellis2-venv\Scripts\python.exe' '.\test\trellis_pipeline_load_test.py'
```

The first loads and executes the real DINOv3 encoder on CUDA. The second loads the offline 512 TRELLIS.2 pipeline and runs its image encoder, but does **not** generate a 3D asset. Each test has its own minimum available system-memory check. Full TRELLIS.2 generation and its peak memory are still unverified. `test/trellis_backend_test.py` checks transparent-reference validation and parameter forwarding using a substitute renderer; it is not a real GPU render.

See the [model source guide](../docs/MODEL_SOURCES.md) for exact checkpoint locations and the [Windows build guide](../docs/WINDOWS_ARM64.md) for compiled dependency details.
