# Runtime map for maintainers

This folder contains Forge-owned adapters and process supervision. It is not a copy of the upstream model repositories. For model file origins, revisions, hashes, and restoration commands see [Model sources and restoration](../docs/MODEL_SOURCES.md). For native build changes and dependency paths see [Windows ARM64 runtime and rebuild notes](../docs/WINDOWS_ARM64.md).

**Chained renders.** A job may declare `request.referenceFrom = { jobId }` (stored also in the `depends_on` column). `JobQueue.tick` resolves it for the job at the head of the queue: while the earlier render is open the job keeps waiting; when it completed, `resolveChainReference` stages its output with `stageProjectAsset` and rewrites the request; a failed earlier render fails the job ("Dependency failed."); a cancelled one cancels it (`cancelDependents`, also run on `cancel` and `resolve`). `enqueueChain` inserts 2 to 4 validated steps in one transaction. `three-d-chain.js` builds the two 3D recipes (SAM cutout then 3D, Qwen image then 3D). Nothing here loads a model; each step is admitted by its own engine's memory checks.

**Queue order and reordering.** The scheduler always takes the open job with the lowest `COALESCE(queue_rank, rowid), created_at, rowid` (`QUEUE_ORDER_SQL` in `queue-order.js`; every read of the open queue in `jobs.js` uses it, and a test guards that). `queue_rank` is a nullable REAL column added by the usual `ALTER TABLE` migration: rows from before it stay NULL and sort by insertion order, and a new job gets a rank above every stored rank and row id (`NEXT_RANK_SQL`, inside the INSERT). `JobQueue.move(id, body)` (HTTP `POST /api/runtime/jobs/<id>/move`, MCP `forge_move_job`) moves one job in a single `BEGIN IMMEDIATE` transaction by writing one rank between its new neighbours' ranks, so it is O(1) and rewrites no other row. When two neighbours leave no room for a midpoint (gap under 1e-6) the open jobs are renumbered once in the same transaction. The body is exactly one of `{to: 'next'|'top'|'end'}` (`next` and `top` both mean first in the waiting line), `{before: id}`, `{after: id}` or `{direction: 'up'|'down'}`, plus optional `expectedRank` (the `queueRank` the caller saw, or `null`) and `expectedAnchorRank` for compare-and-swap. Rules: only `queued`, `waiting_engine` and `waiting_memory` jobs with no `remote_id` move (409 `not_movable` otherwise, 404 for an unknown id, 400 `invalid_request` for a bad body); jobs that cannot move keep their place and never move behind a waiting job that was ahead of them; a render still waiting for its source (`depends_on` with no staged output) is clamped to just after that source and the answer says so (`clamped`, `note`); moving a source behind renders that wait for its output carries those renders along (`carried`). A move changes no status, lease or claim: a running job is untouched and the order applies to the next claim. A stale `expectedRank` or a lost race answers 409 `stale` with the fresh `order` and `ranks`, and nothing is written. A successful move logs `event=queue_move` with the type, status, job id, position and count only. The answer is `{moved, position, count, order, ranks, clamped, carried, renumbered, message, job}`; `GET /api/runtime/jobs` already lists jobs in scheduler order and carries `queueRank`. The planning half of `queue-order.js` is pure and is reused by the studio page (`src/queue-reorder.js`) to show a move before the runtime answers.

**Crash and power-loss safety.** `durable-file.js` is the one write protocol for artifacts and small state files (stage in the same directory, `fsync`, rename or link, flush the directory where the platform allows, `verifyOutputFile` by size and signature). `durable-db.js` is how every database opens (`synchronous`, `busy_timeout`, a once-per-process `quick_check`, quarantine as `<name>.corrupt-<timestamp>` and restore of the newest valid backup) and how backups are taken (`VACUUM INTO` from a separate read connection); `backup-manager.js` schedules them under `.forge-runtime/backups/`. `session-state.js` and `studio-lifecycle.js` (used by `../server.js`) keep the clean-shutdown marker, the stop signals, the stop-request file written by `stop-server.ps1` and the tray, and the 6 second shutdown deadline. `crash-loop.js` stops `host-supervisor.js` and `supervisor.js` from restarting a failing process forever and `recovery-needed-server.js` answers on the studio port instead. `recovery-events.js` is the append-only journal; `recovery-sweep.js` finds and (only for stale `.tmp`/`.part` files that no open job names) removes staging leftovers; `job-recovery.js` classifies jobs and verifies a saved output; `recovery-report.js`, `recovery-service.js` and `mcp-recovery-tools.js` serve the Recovery report and its confirmed actions. See [Resilience](../docs/RESILIENCE.md).

An unverified or missing remote job ID must not be treated as proof that a render stopped. Preserve an `interrupted` or unknown outcome for review. Do not clear a persisted model-load barrier merely because a request timed out; verify the relevant service is no longer loading first.

## Settings registry

User-facing behaviour toggles live in one typed registry, `runtime/core-settings.js` (documented key by key in [docs/SETTINGS.md](../docs/SETTINGS.md)); the Settings dialog, `runtime/settings-service.js` (`/api/settings`) and `runtime/mcp-settings-tools.js` all use it. A value is an explicit environment variable (locked, never overridden), then a row in `settings_overrides` in `.forge-runtime/settings.sqlite`, then the default; AI assist models, `asr-latency.json`, keep awake and the language preference keep their own stores and the registry adapts them. Consumers read `getSetting(key)`, which caches saved overrides for 1.5 s and is shared between the host, the queue worker, the supervisor and the job processes through SQLite. The worker passes functions, not booleans, to the preparation modules (`autoStart`), to `JobQueue` (`chainUnload`) and to `setHostMemoryPolicySource` (`model-load.js`), so a change applies to the next job without a restart; the pure forms (a boolean, an `env` object) remain for tests. Engines started by Forge receive saved `memory.hostPolicy` and `world.fullPrecision` values through `engineEnvironment()` in `engines.js`. Do not read these variables directly any more, do not add credentials, consent, security, network, path or destructive controls, and do not let a settings change stop or start an engine. Every change is audited in the append-only `settings_audit` table.

## Engine integration pattern

Engine names follow the model in files such as `hunyuan_backend.py`, `hunyuan_worker.py`, `hunyuan-preparation.js`, and `hunyuan-job.js`. The Python backend handles model-specific loading/inference, the worker owns the local HTTP service and busy state, the preparation code checks resources and starts or loads the service, and the job adapter transfers inputs and outputs to the durable queue. Not every engine uses all four pieces; existing companion apps have their own APIs.

`*_backend.py` modules are not complete resource managers. Use their corresponding worker/admission path rather than importing one in the main HTTP process. Preserve CUDA-only inference requirements; CPU-side parsing, serialization, and image preprocessing can still be necessary. Model source paths and the installed engine variants are recorded in the [model guide](../docs/MODEL_SOURCES.md).

`auto-memory.js` helps the leased queue recover from insufficient GPU memory. It considers only Forge-owned loaded workers with authenticated atomic stop guards and verified idle state, prefers workers not needed soon, and stops at most one worker before the queue repeats its GPU admission check. It leaves the engine the render itself needs alone, with one exception: when that engine is idle and holds the memory itself (the admission check sets `releasableLoadedModel`, meaning a fresh load would fit the whole GPU), it is the last choice, and only if the studio restarts it by itself (`canRestart`). Queue cancellation, ownership loss, uncertain stop results, external services, realtime ASR/game services, and unguarded companion audio services remain fenced. It does not automatically clear model-load barriers or bypass host-memory admission.

**Memory waits.** The GPU number every admission check compares is `device.freeMiB` from `planModelLoad`, read through `gpu-memory.js` (`readGpuMemory`): never negative, capped at the total, derived from total minus used when nvidia-smi reports free as unavailable, and refused as `gpu_memory_unavailable` when the snapshot is older than 30 seconds. A render whose model is already resident (`prepareImage(request, loaded)`) is admitted on its working memory alone (`details.basis` is `working_memory_only`; otherwise `model_plus_working_memory`). The queue re-reads memory for the waiting render on every tick (about every 5 seconds) and when an engine operation finishes (`resume` ticks at once). Each check writes `details.memoryWait` (`memory-wait.js`): `reason`, `requiredMiB`, `availableMiB`, `shortfallMiB`, `totalMiB`, `estimate` (`conservative_estimate` until a preparer sets `calibrated`), `readingAt`, `since`, `lastCheckedAt`, `nextCheckAt`, `expiresAt`, `checks` and `lastAction` (the last attempt to stop an idle engine, with its outcome and engine). A wait that lasts `memoryWaitLimitMs` (default 30 minutes) ends as `failed` ("Gave up after waiting..."); nothing reached an engine, so Retry is safe and starts a new wait. Automatic stops are logged as `queue.memory.managed`.

`chain-unload.js` decides when a chained render (text to 3D, remove background) should first free the model of the render it took its input from. `JobQueue.freeChainParent` in `jobs.js` runs after the reference is staged and before the child's engine check and memory admission, and reuses `auto-memory.js` restricted to the parent's engine (`only`), so the Forge-ownership, loaded, idle and reservation checks are the same as for "make room". It skips when the switch `FORGE_CHAIN_UNLOAD=0` is set, when the child uses the same engine, or when any other open job needs the parent's engine. A refusal or failure only changes the stage text and is logged as a `chain_unload` queue record; it never fails or blocks the child. It makes one attempt per job and process (`retry` allows another) and re-reads GPU memory (`refreshHardware`) after a stop. Tests: `test/chain-unload.test.js`.

`force-stop.js` and `force-stop-windows.ps1` implement the explicitly confirmed emergency path. Forge captures the owned launcher's Windows PID, creation time, and expected executable; recovered workers use the verified journal identity. The helper pins and checks process handles before terminating the verified tree and reports an uncertain result if it cannot verify completion. The queue fences an affected job as interrupted before termination, ignores late adapter messages, and clears a model-load barrier only after a confirmed stop and the in-flight preparation has finished. Never pass an arbitrary PID from the HTTP client to this path or treat an externally started service as Forge-owned.

**Video (H3).** `video-options.js` is the single description of a video request: it rejects any field outside `VIDEO_REQUEST_FIELDS` (for example `fps`, which the engine fixes at 24) with a 400 that names the field, and it owns the GPU memory budget (`videoGpuBudget`: the chosen `max_vram`, otherwise 12 GiB when the request has reference videos, otherwise the engine's 6 GiB; the 12 GiB figure is a measurement, noted beside the constant). `video-preparation.js` admits a job against that same budget plus the 2 GiB reserve, `video-media.js` sends it to H3 as `--max-vram`, and `asset-metadata.js` records it. `video-failure.js` turns H3's bare `engine exit N` into advice for the two failures Forge can name (a reference that did not fit in the budget, and exit 3221226505 / 0xC0000409); the failure is H3's own final answer, so Retry submits a fresh attempt and Forge never retries by itself. Engine lifecycle: the queue starts the video engine through `service-preparation.js` (`autoStartsService`) when a job is waiting and the engine is unreachable, unless `FORGE_VIDEO_URL` points the queue at a service started elsewhere (`FORGE_AUTO_START_VIDEO=1` opts back in). `POST /api/runtime/engines/<id>/start` starts any one engine (`EngineManager.startOne`, the same rules as start-all: on-demand engines answer `on_demand`). `h3_guard.py` answers `POST /api/forge/stop` itself, with the per-start control token: it refuses new requests, checks that nothing is in flight and that H3 reports no running render, and then exits, which closes its kill-on-close job and ends the whole tree. That makes `POST /api/runtime/models/video/offload` and the **Stop service** button safe for a video engine that this runtime started. It is not an automatic memory-recovery candidate (`auto-memory.js`) because an idle H3 holds no GPU memory; the renderer exists only while a video is being made.

`h3_guard.py`, `asr_guard.py`, and `mammoth_worker.py` contain engine-specific lifetime controls. They do not grant Forge ownership of a service started separately. `sound-credentials.js` reads the configured shared Hugging Face credential for the Forge-owned sound service; do not print the token or include it in queue state, MCP calls, or logs.

On Windows, a restarted supervisor can adopt a TRELLIS.2 worker only after checking its protected token and nonce, listener PID, executable, and process creation time. It rechecks identity before stopping a recovered worker. If a launch was journaled but never bound to a verified process, the record remains unresolved and prevents a duplicate launch; a timeout alone cannot prove it is safe to clear. This first recovery path does not yet cover the other engine types.

## TRELLIS.2 native build

The `trellis-build-*`, `trellis-native-*`, and `trellis-triton-*` scripts build and probe the **existing prepared** Windows ARM64 environment. `trellis-download.py` and `trellis-dinov3-download.js`/`.py` fetch pinned model files and check their hashes. `trellis-patches/` contains source diffs already applied to the local checkouts. See the [build notes](../docs/WINDOWS_ARM64.md) before running any rebuild or attempting to apply a patch.

The current TRELLIS backend is experimental. A local 512 pipeline and its CUDA DINOv3 encoder have been loaded, but the complete model render and its memory budget still need verification. Follow current service and UI status rather than treating an installed checkpoint as a ready engine.

## Operational debugging

Use the studio Diagnostics panel for server metadata, engine logs, and copyable errors. Runtime worker and supervisor restarts are logged under `.forge-runtime/`. Logs can contain prompts and private paths; inspect them before sharing. Do not read or print the shared credentials file during diagnosis.

For automated tests and real GPU probes, see [test/README.md](../test/README.md). A passing substitute-worker test proves protocol/recovery behavior, not generated asset quality or full model compatibility.
