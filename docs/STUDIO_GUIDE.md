# Studio operations and local integration notes

> These detailed notes include observations from a particular Windows ARM64 installation. Model availability, memory budgets, verification status and absolute paths can change. Use the [README](../README.md) for current setup and the [installation guide](INSTALLATION.md) for clean-machine prerequisites.

### World studio

Choose **Worlds** in the sidebar and select a project. WorldGen accepts a text description, one image, or a 360° panorama and exports a Gaussian splat or mesh as PLY. HY-World 2.0 reconstructs a Gaussian-splat PLY from 1–8 views of the same scene. Choose reference images from disk or the asset library, then add the render to the shared durable queue. Completed worlds appear in the project's 3D assets and in the World studio preview, where they can be downloaded, rated, or moved to trash.

**What each generator offers.** WorldGen starts from text, one image or a 360° panorama. **Output** is a Gaussian-splat PLY, a vertex-coloured mesh PLY or a vertex-coloured mesh GLB for game engines. **Panorama width** (1024, 1600 or 2048) is the width of the 2:1 panorama; every pixel becomes one splat or mesh vertex, so 1024 gives about 524 thousand and 2048 about 2.1 million. For text and image starts, **Generation steps** (10–60) and **Seed** apply; a blank seed picks a random one that Forge records and **Reuse settings** restores. Under **Advanced options**, **Prompt guidance** (1–50, blank keeps FLUX's own 7 for text and 30 for images) sets how closely the panorama follows the description, and **Save the generated panorama** also keeps the 360° image as a project image. A saved panorama can be chosen as the **360° panorama** start to build the other output type (or another width) without painting it again. HY-World 2.0 starts from 1–8 views or from one 360° panorama, which it cuts into eight 90° views taken from one point (a shell around the viewpoint, with no depth behind objects). **Resolution per view** is 336, 518, 700 or 952 (HY-World's own default). Its advanced options are **Splat limit** (250 thousand to 5 million, default 1 million; many views at a high resolution exceed the default, which then thins the splats out), **Remove sky** (HY-World's sky model, for outdoor views) and **Drop least-confident points** (0–50 %, default 10; 0 keeps every point).

HY-World only accepts views of one shape, so when the chosen views differ Forge says so and centre-crops each one to the first view's proportions (a failed reconstruction now reports HY-World's own reason). Measured on this installation through the studio: WorldGen text with 10 steps at 1024 took about 3.5 minutes and about 16 GB of GPU memory, and loading FLUX left under 1 GB of system memory free for a while; a panorama start (depth only) took about 20 seconds; HY-World reconstructions of three views took about 35–40 seconds (about 5–10 GB GPU) and eight panorama-derived views about 35 seconds (about 18 GB GPU). The same seed with prompt guidance 3 instead of 7 produced a visibly different panorama.

**What the world page does not offer.** The model cannot do these: WorldGen has no scene-extent or number-of-views control (one panorama becomes one splat or mesh, and its parameters are only prompt, steps, seed, guidance, size and mesh or splat) and no camera-path or video renderer (its demo is an interactive Viser viewer; Forge's own viewer plays that role). Not installed: WorldGen's SHARP splats need the `sharp` package, `pytorch3d` (not built for Windows ARM64) and Apple's SHARP checkpoint downloaded from Apple's CDN, and its background inpainting needs `iopaint` plus its segmentation and inpainting models. The model can do these but Forge does not expose them yet: a WorldGen negative prompt (the FLUX pipeline accepts one through true CFG, which roughly doubles each step), HY-Pano 2.0 text or image to panorama (about 0.8 GB of HY-Pano weights and 54 GB of Qwen-Image-Edit are on disk), HY-World video input and camera or depth priors, its depth, normal, point-cloud, camera and COLMAP outputs, its fly-through video, more than eight views, and the `.splat`, `points.glb`, `mesh.glb` and cubemap exports that the port's `export3d.py` writes. The world page produces one PLY or GLB per render, plus the panorama image on request.

Both integrations use the existing Windows ARM64 environments on the Desktop and require NVIDIA CUDA. The render process exits after each job to release GPU memory. HY-World weights and WorldGen's supporting model cache are centralized under the Studio's `models/` directory in this installation. WorldGen can also use smaller Q5 transformers in `models/worldgen`; the rest of each FLUX pipeline must still be cached. Forge does not download missing model files during a render. Gaussian PLY files use an interactive Gaussian-splat preview, with a point-cloud fallback if the viewer cannot load. GPU memory requirements vary by mode and are not yet calibrated.

The world worker exposes its status and job progress through Forge, its logs appear in Diagnostics, and the MCP tool `forge_queue_world` accepts staged references. CUDA queue tests completed WorldGen text-to-splat, image-to-splat and panorama-to-splat/mesh, and an HY-World four-image reconstruction. An image-to-world test exposed a perspective projection defect in the Windows port; Forge now supplies perspective rays so that the reference is preserved. A render guard stops the active world process if Windows commit memory becomes critically low. These scenes are useful starting points, not guaranteed game-ready geometry: seams, holes and distortion can remain as the viewpoint moves.

The text transformer is [`city96/FLUX.1-dev-gguf`, `flux1-dev-Q5_0.gguf`](https://huggingface.co/city96/FLUX.1-dev-gguf); the image-fill transformer is [`second-state/FLUX.1-Fill-dev-GGUF`, `flux1-fill-dev-Q5_0.gguf`](https://huggingface.co/second-state/FLUX.1-Fill-dev-GGUF). Both inherit the FLUX.1 dev non-commercial license. Place them in `models/worldgen` with those filenames. Forge loads each Q5 transformer when present and retains the original full-precision path if it is absent. WorldGen's local panorama LoRAs and depth model are still required. `FORGE_WORLDGEN_FULL_PRECISION=1` selects the original full-precision path for troubleshooting.

Forge keeps projects, asset creation, and local engine status in one studio. Image, music, sound-effect, video, preset-voice, and Hunyuan shape renders (with optional experimental texture painting) are connected to local engines. Other creation panels and most model controls are previews that help explore planned workflows.

> **Current stage: early integration.** Projects, asset browsing, diagnostics, live GPU memory, the Mammoth decision bridge, and a durable render queue are available. Image, music, sound-effect, video, preset-voice, Hunyuan shape, and SAM still-image segmentation have been verified through Forge in isolated test services and projects. HY-Motion is experimental: a short real queued text-to-motion render has succeeded on CUDA. The video file was produced and saved; its visual quality has not been assessed. Forge can start connected engine services without loading their models and stop supported idle services it owns. Project asset ratings, keep status, rename, reversible trash, managed model removal, and live speech transcription are connected. TRELLIS.2 is an experimental queue workflow; a complete model render remains unverified.

## Quick start

### Windows

Open PowerShell and run:

```powershell
cd 'C:\Users\mreca\Desktop\Game Development Studio'

# Run after installing or updating the app.
npm install
npm run build

# Start the studio in the background.
powershell -NoProfile -ExecutionPolicy Bypass -File .\start-server.ps1
```

Open **[http://127.0.0.1:5173](http://127.0.0.1:5173)**. Starting the studio does not start or load model engines. Open **Models & services** and choose **Start connected services** to start the connected engine services; this does not load their models.

For a dedicated Windows desktop window, double-click `start-desktop.cmd` or run
`powershell -NoProfile -ExecutionPolicy Bypass -File .\start-desktop.ps1`. It
starts the same local Studio service if necessary, then opens the Electron window.
Closing the window hides it; open it again from the Forge notification-area icon.
The desktop app does not bundle the AI models. Its renderer is sandboxed and
loads only this installation's verified local service. If Electron's binary is
missing after a pnpm install, run `pnpm rebuild electron`.

To stop it:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\stop-server.ps1
```

If port 5173 is already in use, choose a different port and use the same port to stop the server:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\start-server.ps1 -Port 5199
powershell -NoProfile -ExecutionPolicy Bypass -File .\stop-server.ps1 -Port 5199
```

The launcher prints the address and log location. It checks for an existing studio server and refuses to take over a port occupied by another service. Node.js 24 and npm must be available; the scripts also require the project dependencies installed in `node_modules` and a current build in `dist`. The runtime uses Node's built-in SQLite support.

For foreground use, run `npm start` and stop it with **Ctrl+C**. Run `npm run build` after changing the React UI. `npm run dev` remains available for development with hot reload. The unified local service is intended for use on this computer and binds to `127.0.0.1`.

### TRELLIS.2 native Windows development

TRELLIS.2 has an experimental isolated rendering service and queue integration. Its CuMesh, FlexGEMM, O-Voxel and nvdiffrast extensions have been built for Windows ARM64 and tested with CUDA. The studio also has a native OpenCV build for image preprocessing and a GPU-only sparse attention implementation. These component tests do not establish that a complete 3D render works.

The isolated environment under `.forge-runtime/trellis2-venv` currently references the PyTorch installation in `C:\Users\mreca\Desktop\Qwen Image Studio\.venv`. It also depends on the installed Visual Studio 2022 ARM64 build tools and CUDA 13.5. Moving or removing those dependencies requires rebuilding or reconfiguring the environment. Run the component checks with:

```powershell
cmd /c runtime\trellis-native-tests.cmd
```

To download and verify the public, pinned image-to-3D checkpoints under `models/`, run `& .\.forge-runtime\trellis2-venv\Scripts\python.exe .\runtime\trellis-download.py`. The approved DINOv3 dependency can be downloaded with `node .\runtime\trellis-dinov3-download.js`, which reads the shared Hugging Face token and passes it to the downloader without putting it on the command line. The scripts resume Hugging Face downloads and will not overwrite an existing file that fails verification. The model inventory measures the main TRELLIS.2 folder, its supporting decoder, and DINOv3, but removal through Forge is unavailable for these preview files until their lifecycle can be managed safely.

The experimental offline 512 pipeline loads the verified files using memory-mapped weights; a real test loaded the pipeline and ran DINOv3 feature extraction on CUDA. The queue, HTTP, MCP, and UI are connected and tested with a substitute renderer. Full TRELLIS.2 renders now complete through the studio (see the 3D capability review below) but the memory budget is not calibrated. Queue preparation requires at least 12 GiB of free system memory, and rendering checks an estimated 24 GiB of free GPU memory plus Forge's reserve. These are conservative estimates, not reservations. The separate background-removal model still requires approved access. The experimental backend therefore requires a transparent PNG or WebP image, which can be prepared using the segmentation panel. On Windows, a replacement supervisor can recover a verified Forge-started TRELLIS.2 worker after its owner crashes; other engine ownership is not yet recovered this way. An unverifiable prior launch is left unresolved instead of automatically starting a duplicate.

### macOS and Linux

Shell launchers are included for environments with Node.js, npm, and `curl`:

```sh
npm install
npm run build
chmod +x start-server.sh stop-server.sh
./start-server.sh
./stop-server.sh
```

Pass a port as the first argument to both scripts if needed, for example `./start-server.sh 5199`. These scripts have been syntax checked but have not been verified end to end on macOS or Linux. Windows-specific features such as keep-awake are not portable as currently implemented.

## Using the studio

The studio is designed for desktop browsers and the Windows desktop window. Layouts also adapt to tablets and phones (a navigation drawer, full-width bottom action bar and 44px touch targets) and were measured in emulated 360–768 px windows without sideways scrolling; they have not been checked on real phones, and the on-screen keyboard on iOS Safari may still cover the Chat composer.

### 1. Create a project

From the overview, choose **New project** and give your game a name. Forge creates a folder under `projects/`, including folders for the asset types currently supported by the project service:

```text
projects/
└── Your Game/
    ├── .forge-project.json
    ├── images/
    ├── video/
    ├── music/
    ├── sfx/
    ├── voices/
    └── masks/
```

The server sanitizes folder names and handles naming collisions. Existing generated files can be placed in the appropriate project folder manually; supported files are discovered for the library. The queue adapters save completed output into the selected project's matching asset folder.

### 2. Explore the creation panels

Choose a panel from the sidebar, select the current project, and experiment with its controls. Draft settings and the draft queue are saved in the browser. In **Images**, **Music**, **Sound effects**, **Video**, **Voices**, **3D models**, **Motion**, and **Segmentation**, **Add to render queue** creates a durable job; **Save as a draft instead** keeps an editable browser draft. Video needs 1–9 reference images (up to 10 MiB each and 40 MiB total). They are saved in the project when the video is queued; select them again after refreshing the page. Image renders can use up to 10 optional reference images; they have the same 10 MiB per-file and 40 MiB total limits as video. Music requires a style and lyrics; use `[Instrumental]` for an instrumental. Forge starts the workers on demand and requests the YuE2 model after checking GPU memory. If memory is short, the job waits and the studio shows the offload dialog. Stable Audio requires gated model access. For a worker started by Forge, it can use a Hugging Face token from the configured shared credentials file; an external worker can use its own configured token, or you can enter one in **Models & services**. Forge reads the token only for its own managed sound worker, passes it locally to that worker for Hugging Face access, and does not write it into the queue, MCP calls, or Forge logs. The worker keeps it in memory while running. TRELLIS.2 can queue an experimental 512-resolution model from a transparent PNG or WebP; a real complete render remains unverified. HY-Motion can queue experimental text-to-motion jobs, with 1–4 variations that are separate jobs using consecutive seeds, and MotionBricks can queue experimental SOMA pose transitions from BVH files, with 1–4 target poses to use (default 4). Target-pose count and the local-root conditioning change need a studio restart before the worker uses them. The game-logic panel can send a structured decision to a running Mammoth service.

GPU memory is the limit that decides whether a model can load. System RAM is only a soft check: the per-engine host budgets are uncalibrated estimates and weights are memory-mapped, so a job waits for RAM only when less than 2 GiB is free (or less than the engine's own budget, if that is smaller). Set `FORGE_HOST_MEMORY_POLICY=strict` before starting the studio to enforce the full per-engine RAM budget instead. If a render or model load runs short of system RAM or GPU memory, the memory dialog shows the requirement, current free memory, and available services. Select an idle Forge-managed service and choose **Stop selected service & retry**; Forge checks it can stop safely and keeps its model files. Repeat if more room is needed. Externally started services must be managed in their own application. Qwen chat has no safe idle-stop guard; use its separate Force stop control only when you accept interrupting a response. These readings are estimates, and stopping a GPU model may not free enough Windows system RAM.

Render timing starts when the engine accepts a job and ends when the asset is saved. Model startup and preparation before acceptance are not included. The queue forecast adds known remaining render times in order, reports unknown timing when a job is preparing or blocked, and shows known render work separately when a full forecast is not possible. Nearby estimates are scaled from completed renders with similar settings and marked **rough**. Without suitable history the studio says so instead of inventing a time. The game-decision and audio-file transcription panels keep their own timing samples locally in the browser; microphone sessions have no fixed end time.

**Reordering the waiting line.** Renders start from the top of **Waiting in line**, one at a time, in the order shown (`#1` starts first). To change the order, use the buttons on a waiting render: **Run next** puts it first in line, and the up and down arrows move it one place. You can also drag the grip handle with a mouse, pen or finger, or use the keyboard: focus the handle, press Space to pick the render up, use the arrow keys (Home and End jump to the ends) to move it, press Space to drop it, or Escape to cancel. The list updates at once and rolls back with a message if the runtime refuses the move; the time estimates are recalculated from the new order. A move only decides which render is claimed next. It never stops or interrupts a running render, and the order is saved, so it survives a restart.

Limits: only renders that are waiting (queued, waiting for their engine, or waiting for memory) and have no engine job yet can move. Running, preparing, interrupted, needs-attention, failed, cancelled and finished renders cannot; their controls are disabled and the tooltip says why. A render that uses the result of an earlier render (text to 3D, remove background) cannot go above that render, and Forge places it right after it; moving the earlier render below the ones that wait for its result carries them along. Several tabs, or an assistant using `forge_move_job`, can reorder the same queue: if a render was moved somewhere else first, the move is refused with a note and the list shows the current order. Renders that need attention still hold up everything behind them until you act on them. If the render at the top was already being claimed at the instant you moved another one first, it still starts first.

Render jobs run sequentially and are stored in `.forge-runtime/jobs.sqlite`. If a job has a known remote ID when the runtime restarts, it resumes monitoring that job. For Forge's Hunyuan3D, SAM, HY-Motion, MotionBricks, and Qwen3-TTS workers, completed files are atomically committed and can be recovered after a worker restart without loading the model or resubmitting the render. Incomplete output is not treated as complete; if the old job cannot be identified, the queue stops for review. Custom external services are not automatically started unless explicitly configured for auto-start. A failed job can be retried; when an engine job ID is known, Forge rechecks that existing job rather than submitting another render. The exception is a SAM segmentation that failed with the engine's own answer (for example "No matching objects were found"): that outcome is final, so Retry clears the old engine job ID and queues a fresh submission (it is marked in the job details as `engine_failed`; failures recorded before this change are not marked and are still rechecked). If the SAM worker was restarted meanwhile, the old job no longer exists, and rechecking it used to stop the queue on an interrupted item. A job whose outcome is unknown (an interrupted submission, a failure after the engine accepted the job that was not the engine's answer, or a reconnect failure) is never resubmitted automatically. Cancelling a retried job now shows "Cancelled." as its stage. If a crash makes submission uncertain, the queue stops on an **interrupted** item rather than automatically submitting a duplicate. H3 exposes only its current job; if it no longer recognizes an accepted job, Forge stops for review even if a similarly named output exists, since the file could be incomplete. Check the relevant engine's own queue, history, and rendering process before resolving it in Forge. Queued or waiting items can be cancelled; cancelling an already running job is not yet supported from Forge. Keep `.forge-runtime/` if you need the queue history as well as `projects/` if you need the output files. The existing engines also retain their own original outputs; Forge copies the selected asset into the project.

Image and video reference files are snapshotted under the project’s hidden `.forge-inputs` directory and retained for recovery and retries. Other reference-file controls are previews; they retain the selected file’s name and size, not the file contents.

### 3. Browse your assets

Open **Asset library** to explore included samples or files discovered in a project. Select a project, then search or filter by type, change the sort order, or switch between grid and list views. Supported media can be previewed or played, and assets can be downloaded. Project asset details also provide a file location you can copy.

Currently indexed formats are PNG, JPG/JPEG, WebP, GIF, WAV, MP3, FLAC, OGG, MP4, WebM, GLB, glTF, FBX, and BVH. BVH motion clips are stored as 3D assets; the **Motion** tab lists them and the **3D** tab lists models and splats. Some 3D formats require an external viewer.

In **Asset library**, **Delete project…** requires the exact project name and moves the entire project folder to recoverable project trash. Waiting, active, and unresolved renders must be finished or resolved first. Use **Deleted projects** to restore it; restoration requires its original folder name to be free. Trashed projects still use disk space. Finish any Megascans imports before moving a project. **Delete all project assets…** instead moves currently recognized assets into that project’s asset trash, keeping the project, unsupported files, and hidden files. Both actions ask for the project name. New renders or imports can create files while an asset batch is running.

Project asset ratings and keep status are stored with the project; sample ratings are browser-local. Delete moves a project file to **Project trash** in the asset library, where it can be restored or permanently removed by clearing the trash after confirmation. Incomplete or unsafe trash records are preserved and reported for review. Asset rename keeps the file in the same project folder, retains its extension, and preserves ratings and render provenance. For a renamed generated asset, the jobs API reports its current `output` path and includes `originalOutput` with the original render location.

#### Reset to defaults

Every creation page, the Worlds page and the Chat options have a **Reset to defaults** link. It stays disabled while the page already uses its defaults. When something differs, selecting it shows an inline confirmation (**Yes, reset** or **Cancel**) before it clears the prompt, settings, chosen files and the model selection for that page. Chat's reset leaves the local engine's context size alone; that setting lives in the engine panel.

#### Mini player

Audio and video previews have a **Shrink to mini player** button. The mini player stays docked at the bottom right while you move between pages, can be dragged or moved with the arrow keys when its grip is focused, and shrinks to a pill. **Back to full preview** returns to the page the preview came from. A repeat button cycles **Never** (stop at the end), **Once** (play one extra time) and **Loop**; the choice is remembered in this browser and also appears on the inline previews.

#### 3D and motion viewer

All 3D formats open in one viewer with a toolbar, an inspector (format, size, vertex, triangle or splat counts, bounding box, animation clips) and, for animated assets, a playback bar. Use ← and → to step through the 3D assets in the current list. Shortcuts work while the viewer has focus: Shift+arrows orbit, Ctrl+arrows pan, ↑ and ↓ or + and − zoom, R resets the view, F frames the model, 1–6 select front, back, left, right, top and isometric views, O toggles auto-rotate, W wireframe, G grid, X axes, B bounding box, S ground shadow, L cycles lighting, C cycles the background, Space plays or pauses, P saves a PNG of the current view, I toggles the inspector, M opens the large viewer or toggles browser fullscreen, and ? lists the shortcuts. Display toggles are remembered per browser. Thumbnails created before this viewer keep their old look until the asset changes, because they are cached by file size and modified time. **Panorama meshes.** A WorldGen GLB is a closed 360° shell meant to be seen from inside, so the viewer opens it inside by default. Forge recognizes these from the stored generation details (WorldGen with a GLB output). For other files it falls back to the shape: a roughly cubic box with almost every triangle facing one centre, which convex closed objects can also match, so the note says when the shape was the only evidence. Inside, the camera stays at the centre and turns in place: drag, or Shift and arrow keys, looks around, and scroll, + and − change the field of view. Panning is not offered inside. The **View from inside** toggle in the toolbar switches to the normal orbit view; the choice is per open asset and is not remembered. Faces draw from both sides while inside.

### Megascans

Open **Megascans** (under _Your studio_) to browse the free Quixel Megascans 3D models that Fab lists and to download them into a project.

- **Models** come from a cache on this computer. Forge reads Fab's public listing data slowly (one request at a time, with pauses) and shows what it has stored: thumbnails, category, formats, file sizes, tags and licence, and, once you open a model, its description, polygon counts and every file Fab offers. Search, tag filter and sort work offline and are kept in the page address (`/megascans?q=&tag=&sort=&page=&listing=`). The list shows 24 models at a time; **Load more** (or scrolling to the end) adds the next 24 and announces it, and only when the whole cache is shown does **Read more from Fab** read one more page. The status line reads like _Cached 3 h ago · 1,240 listings from Fab_, and a model's dialog says _Details cached 2 days ago_ with **Refresh details**. If Fab cannot be reached, everything saved still works and the page says so.
- **Refresh** reads the newest free models (at most once a minute); the page does this once by itself when the cache is older than a day. **Scan catalog** walks Fab's listing pages in the background, 10 pages per run, with progress, **Cancel** and **Resume**. If Fab ever refuses automated requests, Forge stops, says _Fab is blocking automated requests_ with the time it will wait, and keeps working from the cache and the Import flow. It does not try to get around the refusal.
- **Downloading.** Open a model and choose a file under **Download from Fab**, grouped as GLB, glTF, FBX, glTF for Unreal and USDZ, each with its quality (low, mid, high, raw) and size. The GLB at mid quality is recommended: one file, a balance of detail and size for most games. Files over 100 MB ask for a second confirmation; the huge extra EXR texture archive sits under **Advanced** with a warning and cannot be imported. Downloads stay off until you tick, **once**, _I have read and accept the Fab End User License Agreement, the Fab Terms of Service, Epic's Acceptable Use Policy and this listing's licence_ (each is a link). Only you can tick it; untick it to turn downloads off again. Forge asks Fab for a short-lived signed address right when each download starts and never stores it.
- **Prefer to do it yourself?** **Open on Fab** opens the listing in a new tab. Download the file there, then use **Import file** (on the page, on a card or in a model's dialog), or drop the file on the Downloads panel. **Add by address** saves a listing Forge has not read yet.

The **Downloads** panel shows each download or import as waiting, importing, completed, failed, cancelled or interrupted, with a progress bar, speed and an estimated time left. At most 2 run at once and the rest wait. **Cancel** stops one, **Retry** continues a failed, cancelled or interrupted download from the partial file when Fab's servers allow it (otherwise it starts again), and **Dismiss** forgets a finished one. A download that was running when the studio stopped is shown as _interrupted_ and is never restarted by itself.

Forge checks the size and file types, rejects archives that contain executables or unsafe paths, and checks that there is enough free disk space. It then writes the models and textures to the project's `3d/` folder (archives go into a `megascans-<name>-<id>` folder) and records the listing, licence (name and link), seller and attribution so the Asset library details read _Imported from Fab / Quixel Megascans_. Texture files from an archive also show up in the library as images, and the 3D viewer loads each model on its own, so FBX textures may not appear. If YuE2 is running, its model can also be loaded from **Models & services**. Forge first checks free GPU memory against the existing CUDA pipeline's 24 GiB budget plus a 2 GiB reserve. For the first Qwen Image render, Forge checks a conservative, uncalibrated 48 GiB working budget plus a 2 GiB reserve. One isolated 512×512, 12-step run sampled a peak of 34,900 MiB across all GPU processes; other settings and workloads can use more. Externally started services and other engine types must currently be managed in their own applications. The memory check is a snapshot, not a reservation against other processes. Manual and queue-triggered YuE2, Stable Audio, and Qwen3-TTS loads pause later renders until the worker reports that loading finished or failed; the barrier survives cancellation and runtime restarts. If a crash leaves it stuck, use **Clear after checking** only after verifying the named engine is neither loading nor queued to load.

Memory admission currently supports a single identifiable NVIDIA GPU; the separately reported NPU is excluded. If multiple GPUs are present or the target GPU's free memory cannot be verified, Forge refuses the load rather than using a different device's reading. Per-engine GPU UUID mapping for multi-GPU systems is not yet implemented. When memory is short, the dialog also identifies busy services such as an active video render, which must finish before they can be stopped.

The image panel can override output width, height (32 to 2752 pixels, multiples of 32), sampling steps and seed, and accepts up to 10 reference images (choose files or pick project assets; the references are numbered in order and the prompt can refer to them as image 1, image 2 and so on). **Transparent background** asks Qwen for an RGBA PNG using its documented prompt wording (Forge adds the wording when it sends the job and saves only your own prompt). **Match the last reference's shape** omits the width and height so Qwen derives about a megapixel at the last reference's aspect ratio. An optional negative prompt enables classifier-free guidance above 1 (negative prompt guidance 1.1 to 10, default 2); leave it blank for Qwen's default unguided mode. A blank seed is replaced with a random one when the job is queued and recorded with the asset. Verified through the studio UI on 2026-11-07 (BF16 model, 512 pixel renders, 8 steps): the same prompt, seed and settings gave a byte-identical PNG a second time, including with a reference image and a matched size; a cold first render took about 2 minutes (about 97 seconds loading the model, peaking near 39 GB of GPU memory), a warm 512 pixel render about 6 seconds, a 1-megapixel reference edit about 21 seconds, and a 2752 × 1536 render at only 4 steps 45 seconds with about 73 GB of GPU memory in use. Variations, LoRA files, the KV-cache switch, a reference size target and a custom sampling schedule are described under "Newly exposed engine options" below. Not available in Forge: a painted-mask input (the engine has none; a mask or marked-up image can be added as a reference and described in the prompt), strength sliders (no engine input) and a scheduler list (one scheduler, flow-matching Euler with dynamic shifting). The video panel offers H3's supported 8, 12, 20, and 30 sampling steps and an optional seed (0 to 2147483647). Verified through the studio UI on 2026-11-07 (portrait and landscape, 56 and 124 frames, 8 steps): the same description, reference, settings and seed gave a frame-for-frame identical video and soundtrack, and another seed gave a different one. A 2.3 second 608 × 352 render with 8 steps took about 2 min 45 s, and a 5.1 second 352 × 608 render from two references with 8 steps took 5 min 35 s. Both peaked near 11.8 GB of GPU memory across all processes; free host RAM fell to about 1.5 GB and 0.6 GB respectively on a 31 GB machine, so close other large engines before longer clips. The WebM holds VP8 video at 24 frames per second and generated 32 kHz stereo PCM sound, so describe the sound in the scene description. Refer to the references as <Picture 1>, <Picture 2> and so on, in the order they are listed. Music fine-tuning exposes duration, synthesis steps, guidance, negative style, title, seed, an optional ABC melody score, and song-token sampling (temperature, top-p, top-k, repetition penalty). Qwen3-TTS currently uses the 1.7B CustomVoice model with nine preset speakers (Ryan and Aiden for English, Vivian, Serena, Uncle_Fu, Dylan with a Beijing accent and Eric with a Sichuan accent for Chinese, Ono_Anna for Japanese, Sohee for Korean; any speaker can read any of the ten supported languages or Auto) and optional voice direction. Fine-tune voice exposes the speech token limit (64 to 4096; about 12.5 tokens, or 80 ms, per second, so 1024 is roughly 80 seconds), temperature, top-p, top-k, repetition penalty, a sampling mode, sub-talker sampling (below) and a seed. A random seed is chosen at queue time and recorded with the asset; the same seed, text, and settings repeat a render bit for bit (checked on this machine). Speech that reaches the token limit stops mid-sentence; the queue row then says so. A render holds up to 1,000 characters and is not split automatically; an 841-character English passage became about 61 seconds of audio in about three minutes. Output is a completed 24 kHz mono WAV, not a live stream; Convert in the asset library makes other formats. **Voice cloning** (Base checkpoint) and **voice design** (VoiceDesign checkpoint) are separate modes on the Voices page. Cloning takes a 3 to 30 second project WAV, FLAC or MP3 and the exact words spoken in it, typed by you (Forge does not transcribe it yet), plus a required confirmation that you have the right to use that voice; Forge copies the clip when you choose it and records the transcript, not the audio bytes. **Voice only** (a checkbox in clone mode; `clone_voice_only` over MCP) clones from the clip's speaker embedding alone, with no transcript: the transcript field becomes optional and is not sent, so it suits a clip whose exact words you do not know. This is the Qwen3-TTS x-vector-only mode; it usually matches the speaker less closely than a transcript-matched clone, and Forge has not measured that gap. Design takes a description of up to 500 characters. A mode whose checkpoint is not staged is disabled and shows `.\install.ps1 -Models tts-base` or `tts-voicedesign`. The worker holds one checkpoint at a time: switching modes unloads the resident checkpoint, then loads the new one after GPU-memory admission (the resident checkpoint is counted until it is unloaded, so a switch can wait for memory). Clone and design were rendered on the real Base and VoiceDesign checkpoints on 2026-11-08 (a design with the same description and seed repeated bit for bit after a checkpoint swap, and a clone's pitch and spectral shape followed its reference clip); this was measured numerically, not judged by ear. The transcript-free "voice only" clone option (Qwen3-TTS x-vector-only mode) was added after this measurement and has not been rendered on the real checkpoint yet. Speed or pitch have no separate control (use voice direction). Its isolated Python environment currently shares CUDA libraries from the existing `Snapdargon-DJ/.runtime` installation, which must remain available.

SAM 3.1 is connected for text-prompted still-image segmentation. Choose one PNG, JPEG, or WebP image, describe the object, choose which matches to keep and which picture to save (see **SAM match options** below), and adjust confidence. Results are saved under the project's `masks/` folder. The SAM 3.1 checkpoint and the separate SAM 3 checkpoint were verified against their upstream SHA-256 hashes. A real Windows ARM64 test loaded SAM 3.1, isolated a truck in Meta's example image, and saved a transparent PNG through the MCP and durable queue; its background alpha was verified. That single sample does not establish general output quality. On 2026-11-08 the page's two outputs (transparent PNG and mask PNG) were run through the studio UI on a 1024 × 1024 picture (the cutout kept 7.3 percent of the pixels with real alpha and an identical mask; a three-apple picture gave three instances merged into one mask). The model supports only a text description here: Forge does not offer box prompts, point prompts, several descriptions per image, a separate file for every match or video tracking (see **What box and point prompts, several descriptions and video tracking would need** below). SAM 3.1 matches concrete nouns, not generic words (see the 3D section for a measurement of the default "main object"). Forge starts the isolated worker on demand, checks 9 GiB free system memory and an estimated 12 GiB GPU budget plus 2 GiB reserve before loading, then checks additional working memory before a render. These budgets are conservative estimates, not reservations. A busy Forge-managed SAM worker cannot be offloaded. The Python 3.14/NumPy 2 environment is outside SAM's declared NumPy range and remains experimental. Point and box prompts and video tracking are not connected.

**SAM match options.** SAM usually returns several matches for one description, each with a mask and a score; before this change Forge always merged all of them into one mask. The Segmentation page now has **Which matches**: _All matches combined_ (the default and the old behavior), _Only the best-scoring match_, _Only the largest match_ (most pixels), and _The best-scoring matches, up to a limit_ (**Most matches to keep**, 1 to 50; fewer are kept when fewer are found). Matches with an empty mask are never chosen. The request fields are `select` (`all`, `best`, `largest`, `top`) and `max_instances` (required with `top` and rejected otherwise); the default `all` is not stored, so older requests keep their exact shape. **Export** gained two pictures besides the transparent cutout and the black-and-white mask: _Outline overlay PNG_ (the original picture, nothing made transparent, with a 2 to 8 pixel pink border drawn inside each kept match; the border is not drawn along the image edge) and _Cropped cutout PNG_ (the transparent cutout trimmed to the bounding box of the kept matches plus 5 percent padding, at least 4 pixels, clamped to the image). A cropped cutout can feed a chained 3D render like a transparent one (`output: "transparent"` or `"cropped"`); a mask or an outline cannot. When a render finishes the worker reports how many matches it found and used and their scores (up to 20, best first, from the model's own scores); the queue row shows "Found 4 matches, 2 used. Scores of the kept matches: …", `forge_job` returns it as `details.result`, and the asset's generation details gain _Matches found_, _Matches used_ and _Scores of kept matches_. A job recovered after a worker restart has no such report. The SAM worker now lists `match-selection` in `features` on `/api/status`; the job worker refuses a request that uses a new option (a match choice other than all, or the outline or cropped output) when the running worker does not list it, because an older worker would ignore `select` and return every match. Stop the SAM 3.1 engine and start it again after updating (the job fails before anything is submitted, so Retry is safe). **Tested with substitute models only:** the selection, outline and crop code is unit-tested with fake mask tensors and a fake worker, and the queue paths with a fake SAM service; no real SAM render has been run with these options, so the visual quality of the outline (color, thickness) and the crop padding, and whether the model's scores order matches as expected on real pictures, are unchecked.

**What box and point prompts, several descriptions and video tracking would need (not built).** These are not connected today. What each would take, from the SAM 3 source in `.forge-runtime/sam3-src` and Forge's worker:

- _Box prompts._ `Sam3Processor.add_geometric_prompt(box, label, state)` exists for the image detector: a box in normalized `[center x, center y, width, height]` with a positive or negative label, applied after `set_image` (it uses the text prompt "visual" when none is set). Needed: a request field for boxes (validated 0 to 1, count limited), a way to draw them on the chosen picture in the browser (a canvas overlay with keyboard-operable alternatives, a positive/negative toggle, drawing on an image that is only held in the page until it is staged), the worker's `SegmentRequest` and `segment_image` to call it, and tests with fake processors. Roughly a day of UI work plus a day for the worker and tests. Whether the detector built from the multiplex checkpoint (Forge loads only the `detector.` weights) segments well from boxes alone is unverified and needs a real run.
- _Point prompts._ The image processor has no point API (`input_points` stays `None`). Points belong to the SAM-1-style interactive predictor (`inst_interactive_predictor`, `sam1_task_predictor.py`), which Forge's detector build does not construct. Needed: building and loading that predictor from the checkpoint (extra weights and memory not measured, and not confirmed to be in `sam3.1_multiplex.pt`), its own admission budget, then the same request, UI and test work as boxes. This is the largest of the image-level items; treat it as a research task first.
- _Several descriptions per image._ The cheap one on the model side: after `set_image` once, `reset_all_prompts` and `set_text_prompt` can run again, so extra descriptions cost little GPU time (not measured). Needed: a `prompts` list in the request (a limit such as 8, each 1 to 1000 characters, stored beside the existing single `prompt` so old rows stay valid), a decision on outputs (one file per description, named by it, or one merged mask; one file per description means a job with several outputs, which the queue's single `output` field does not support today, so either several jobs sharing one `set_image` per description or a queue change), a list editor on the page, and per-description match reports. About two to three days, mostly the multi-output decision.
- _Video tracking._ `build_sam3_multiplex_video_predictor` builds a predictor on `Sam3BasePredictor` (requests `start_session`, `add_prompt`, `propagate_in_video`) that tracks objects through frames. Needed: loading the tracker part of the model (Forge loads only the detector; its size and whether it fits next to other workers have not been measured), a video input (frame extraction and limits), a new job type or a new `segmentation` mode with per-frame or per-object outputs (masks per frame as a sequence or a video), progress reporting and cancellation, a viewer for the result, and a GPU and host memory admission budget. This is a new workflow of a week or more, not an option.

MotionBricks is an experimental SOMA transition workflow. Its SOMA checkpoints and the SOMA and G1 ONNX models are stored under `models/MotionBricks/` and verified against NVIDIA's published hashes. The queue remains paused until the expected streaming model reports ready; an uncertain startup retains the barrier for review. The service is not automatically restarted after a crash because a restart would need a fresh GPU check. Forge-managed ASR runs behind a local guard that refuses offload while HTTP or WebSocket clients are connected; an idle service can be selected in the GPU-memory dialog. On Windows, the guard owns the CUDA engine through a kill-on-close job to prevent an orphaned model process after a guard crash. Externally started speech services are not controlled by Forge.

On Windows, H3 services started by Forge run behind a guard that owns both the H3 server and its renderer in a kill-on-close job. If the guard or H3 server crashes, its renderer is stopped and the supervisor can restart the service without automatically resubmitting the old render. Overlapping video uploads are checked again immediately before launching a renderer. The guard uses the locally configured H3 server and refuses to start if the expected H3 server code changes. A separately started H3 service is not modified or managed by Forge. The guard, restart, and crash cleanup have been tested with a substitute renderer; the real H3 server has been smoke-tested behind the guard without running a video render.

Live check (2026-11-08): the installed Mammoth engine refuses a state plus its longest question above 4,096 tokens (its message says so), not the 16,384 tokens in the upstream README; Forge does not pre-check the count. Three questions in one request took about 0.8 s against about 0.27 s for one, so no shared-prefill saving was measured. The game-logic panel can ask up to 16 named questions about one game state in a single request (the extra questions are kept in the panel, not saved with the draft). Each question is validated on its own and errors name the question. `forge_game_decide` requires `state` as text. Mammoth can be started from the game-logic panel, `POST /api/runtime/models/game/load`, or the `forge_load_game_model` MCP tool. The managed worker imports the existing Mammoth Studio app without its automatic download or model load, checks for CUDA and llama.cpp GPU offload, and loads only after Forge checks an estimated 24 GiB GPU budget plus a 2 GiB reserve and a soft 2 GiB free system-memory floor (the default host-memory policy; set FORGE_HOST_MEMORY_POLICY=strict to require the full 6 GiB budget). Admission runs before the Mammoth worker starts, so a refused load starts no process. These are uncalibrated estimates, not reservations. A persistent queue barrier protects uncertain loads; a managed worker refuses to stop while loading or handling decisions, including work left running after an HTTP cancellation. An independently started Mammoth service is left untouched. The guard has been tested with the real application unloaded and with simulated loads and decisions; a full managed GPU model load has not yet been verified. The existing external Mammoth decision bridge has been verified separately. After a failed managed load, offload the idle worker and retry with a fresh process. If a crash leaves a barrier stuck, check the worker and logs before explicitly clearing it.

The **Voices** page offers live microphone transcription with partial and final English text, plus local audio-file transcription (up to two minutes and 25 MiB). Transcripts stay in the browser until you choose to save or copy them. On the Voices page, **Recognition options** exposes the same two settings; word timing applies to WAV files chosen from the asset library and transcribes them in one request (the other files are streamed). The English-only Nemotron model has no language setting. Realtime `endpointing_ms` has no effect because the server is not started with endpointing. On this machine a 60-second recording transcribed in about 1 second as one request and in about 16 seconds when streamed from the browser; word error rate on speech from Qwen3-TTS was 3 to 5 percent. MCP exposes `forge_load_asr_model` and `forge_transcribe_project_audio`. The proxy only accepts local requests and same-origin browser connections.

Each creation panel shows matching recent assets from the selected project. Keep and rating are saved with the project. Trash can be undone immediately or restored later through **Project trash** in the asset library. Engine workers run as separate processes. The main Forge supervisor retains their process handles when the HTTP host or runtime restarts, so it can keep managing its own workers after those failures. ### Refreshing the capacity figures

The project site (`site/index.html`) has a **Model weight capacity** section that counts the models and sums their size on disk. The figures are measured, not typed. After models are added, removed or updated, run this on the reference machine, with the studio running so the GPU size and the studio's own storage scan can be read (two read-only GET requests to `/api/runtime/hardware` and `/api/runtime/model-storage`):

```powershell
npm run site:capacity
```

This runs `node tools/model-capacity.mjs`. The tool walks `models/` without following links, adds up the size of every regular file, and maps each folder to one row (a model card, or a supporting checkpoint or cache) with the table at the top of the script. It writes `site/model-capacity.json` and rebuilds the no-JavaScript table in `site/index.html` between the `capacity:static` markers, so commit both files together. The page draws its tiles and table from the JSON in the browser. Nothing is published until the change is pushed. `--no-studio` skips the studio (the saved GPU size is reused) and `--render-only` only rebuilds the table from the existing JSON.

The tool fails when a folder over 100 MiB is not in its table, so a new model cannot be left out: add it to `ROW_DEFINITIONS` with the id of its site card. Run `node --test test/site-capacity.test.js` afterwards; it checks the JSON, that the static table matches it, and the sorting in jsdom.

Sizes are file sizes in bytes (GiB = 1,024³ bytes, GB = 1,000³ bytes), not parameter counts or loaded GPU memory. **Why the total differs from the Models page:** NTFS hard links give one file several names, and the studio's storage scan (which feeds the Models page) adds every name, while `du` and this tool count each file once. On 2026-11-08 the studio scan reported 381.48 GiB for 22 folders and the tool reports 363.70 GiB (390.52 GB): the 18.08 GiB difference is hard-linked names counted twice (in `hf-cache`, `MiniMax-H3` and `MotionBricks`, plus one file shared by `ComfyUI` and `MiniMax-H3`), less 0.30 GiB in `Qwen-Image-2.1-LoRA`, a folder the studio scan does not cover. The tool records this reconciliation in the JSON.

## Notifications and keep-awake

On Windows, the Studio starts a notification-area icon with controls to open,
minimize or maximize the Studio window, offload a verified idle Forge-managed
model, and stop the Studio after confirmation. Offloading uses the same queue and

model workers may remain running. The open, minimize, and maximize commands

## Files and persistence

### Automatic model management

The render queue starts its supported engine and loads the model when a job needs it. Models can stay loaded for reuse. If a job does not have enough reported GPU memory, Forge tries to make room by stopping one verified idle, Forge-managed engine at a time, then checks memory again before continuing. It favors keeping models needed by the next queued jobs. If the idle engine that holds the memory is the one the job needs and a fresh load would fit the GPU, Forge stops it last and the studio restarts and reloads it by itself. Forge never stops a busy engine or a process it did not start. A job that waits for memory shows the numbers (needed, available, whether the need is a conservative estimate), when it last checked and when it checks next, and checks about every five seconds. After 30 minutes it stops waiting and shows as failed with the reason; free memory or close a service, then retry. The queue shows what it is doing; model files remain on disk.

**Freeing the first model of a chain.** In a text-to-3D chain (Qwen Image, then TRELLIS.2 or Hunyuan3D) and a remove-background chain (SAM 3.1, then a 3D model), Forge unloads the first model once its output is staged and before the second model is admitted and loaded. The queue shows "Freeing memory from the finished Qwen Image render..." (or SAM 3.1), then "Freed memory from the finished ... render." It only does this when all of these hold: the render is the chained one and its parent has completed; the parent's engine is loaded, started by Forge, and idle (the same guarded stop the memory dialog and "make room" use, which rejects active work); and no other open render in the queue needs that engine, so a second Qwen Image render queued behind the chain keeps Qwen Image loaded. After the stop Forge re-reads GPU memory so the 3D admission sees the freed space. It is best effort: if the stop is refused (engine started outside Forge, busy, already unloaded) the 3D render simply continues, and if the stop fails the job's stage says so; the render never fails because of it. Each chained render gets one attempt per runtime process (a retry gets another). Set `FORGE_CHAIN_UNLOAD=0` (also `false`, `off` or `no`) in the environment of the studio to turn it off and keep both models resident; it is on by default. Unloading means the next Qwen Image or SAM 3.1 render has to load that model again. Verified with substitute engines only; the effect on real GPU, host RAM and commit memory has not been measured (see the manual test plan in the handoff for this change).

Automatic stopping is limited to guarded image, voice, 3D, segmentation, and motion workers, whose stop operation atomically rejects active work. Forge never automatically stops externally managed services, realtime speech recognition, or the game-logic service. YuE2 and Stable Audio can still be started on demand, but their current companion services lack the guarded stop needed for automatic offloading; the memory dialog offers manual choices if they are blocking a render. Memory readings are snapshots, and a render can still require attention if memory is unavailable or an engine cannot safely stop. System-memory admission checks remain separate.

If a Forge-started service stops responding, open **Models & services** and choose **Force stop…** for that service. After confirmation, Forge verifies its recorded Windows process identity and terminates its verified process tree. An affected render is marked **interrupted** and blocks the queue until you review and resolve it; any active work may be lost. Saved assets and model files remain on disk, and GPU/system memory readings can take a moment to update. The control is unavailable when ownership cannot be verified or the service was started outside Forge. If a model-load barrier still needs review, inspect the engine and use the existing barrier control before continuing.

### Converting image and audio assets

Open a project asset in the library, or use **Convert** beside a recent creation. Choose a format and select **Convert & save copy**. The original stays untouched; each copy gets a unique name in the same project folder and can be downloaded from the result or asset library. Images can be saved as PNG, lossless WebP, JPEG, BMP, or TGA. Audio can be saved as 24-bit WAV, FLAC, MP3, Ogg Vorbis, or Ogg Opus. Videos (WebM from H3, or MP4) can be saved as an H.264 + AAC MP4, which game engines, editors and phones play, or as a silent looping GIF (about 12 frames per second, up to 480 pixels wide, at most about 25 seconds); an MP4 copy keeps the generation details of the video it came from. Forge creates a thumbnail preview for TGA files. JPEG and BMP fill transparency with the selected background color. Opus is resampled to 48 kHz when its input rate is unsupported.

3D models convert between GLB, glTF, OBJ, PLY and STL; see [the 3D section below](#3d-chained-renders-text-to-3d-background-removal-trellis2-pipelines-and-export).

JPEG encoding attempts NVIDIA GPU acceleration with nvJPEG through the installed CUDA-enabled torchvision, then falls back to the CPU if unavailable. The result reports the encoder actually used. Other formats use CPU codecs. Conversion is separate from the render queue.

On this installation conversion uses the existing `Snapdargon-DJ/.runtime/python.exe` with Pillow, soundfile/libsndfile, NumPy, PyAV (its bundled FFmpeg libraries encode H.264 and AAC for video, so a separate ffmpeg is not needed), and optionally CUDA PyTorch/torchvision. Set the `FORGE_TRANSCODE_PYTHON` environment variable before starting Forge to use another compatible Python runtime. Missing codecs or an unavailable runtime result in an error in the conversion panel; no original is overwritten.

### 3D: chained renders, text-to-3D, background removal, TRELLIS.2 pipelines and export

These features were added together on 2026-11-08. They are covered by unit, UI, MCP and queue tests that use substitute engines (including an end-to-end chain through the real queue and job workers against fake SAM, Qwen, Hunyuan and TRELLIS.2 services). The Hunyuan3D side of chaining, background removal, the painter options and format conversion was then run for real on 2026-11-08 (see **Verified on the real stack** below); TRELLIS.2 chains, text-to-3D and all four TRELLIS.2 pipelines were then run for real as well (see **Verified on the real stack, TRELLIS.2 and text-to-3D** below).

**Chained renders (job chaining).** A render can take one of its references from the output of an earlier render. Set `request.referenceFrom = { "jobId": "<earlier job id>" }` on a `3d`, `trellis`, `segmentation`, `images` or `video` job and leave that reference out (`references: []` for the single-reference types; an image or video render may list other references too, and the chained one is appended last). The earlier render must be an `images` render or a `segmentation` render with `output: "transparent"` or `"cropped"` (a mask or an outline cannot be a reference), in the same project, and not already failed or cancelled. `POST /api/runtime/jobs/chain` with `{ "steps": [...] }` (2 to 4 steps; a later step writes `referenceFrom: { "step": 0 }`) validates every step first and inserts them in one transaction, so a rejected step leaves nothing queued; the `forge_queue_*` 3D tools and the 3D page use it.

- **Waiting.** The queue is first-in first-out and an earlier render always runs before a later one, so the chained render simply waits its turn. Its status stays `queued` with the stage "Waiting for the render it depends on."; the queue panel and the /queue page list it directly under the render it waits for, mark it "waiting for earlier render" and say what it waits for. Estimates count the pending reference, so a waiting render matches the timing history of finished siblings.
- **Starting.** When the earlier render has completed, Forge stages its output file (following a rename of the asset) as the reference, records `referenceFrom.output` on the job, and the render proceeds normally. The staged copy is a snapshot, like any reference.
- **Failure.** If the earlier render failed, the chained render fails at once with the stage "Dependency failed." and a message that quotes the reason. If its output is missing, too large (staging allows up to 10 MiB) or not a PNG/WebP where TRELLIS.2 needs one, it fails with that message. Retrying the earlier render also requeues the renders that failed only because of it.
- **Cancelling.** Cancelling (or marking an interrupted render cancelled) also cancels, recursively, the renders still waiting for its output. Renders that already received their reference are independent and keep going. The Cancel button's tooltip says how many will be cancelled.
- **Restarts.** The dependency is stored in the jobs database (a new `depends_on` column, added automatically; older databases and rows keep working) and in the request, and the pending state is re-evaluated by the next queue check.
- **Records.** The finished asset's generation details gain "Made from render" and "Made from file" settings, and its references list the staged picture.

**Remove the background first (3D page).** TRELLIS.2 requires a transparent PNG or WebP, and Hunyuan treats a fully opaque picture as all object. Tick **Remove the background first (uses SAM 3.1)**, optionally change **What to isolate** (default "main object", which found the subject on three of four test pictures where "the main object", "object" and "subject" found none; naming the thing, such as "apple", is far more reliable), and Forge queues a SAM 3.1 transparent cutout and then the 3D render chained to it. When a file is chosen the page measures its alpha channel in the browser; if it already has a real transparent background (at least 1 percent of pixels mostly transparent, the same rule the TRELLIS.2 worker applies) the box is disabled and says so, and only the 3D render is queued. A JPEG is known to be opaque; if the browser cannot decode the file the box stays available. SAM 3.1 and the 3D model load one after the other, and if SAM finds nothing the 3D render stops with that message. Forge frees SAM 3.1 before the 3D model loads when it can (see **Freeing the first model of a chain** under Automatic model management). MCP: `removeBackground: { prompt, confidence }` on `forge_queue_trellis` and `forge_queue_hunyuan_shape`.

**Text-to-3D (3D page, "A description").** Choose **Start from: A description** (both models). Forge queues a Qwen Image 2.1 render of your description at 1024 × 1024 with a transparent background (always on; image steps default 25, editable from 1 to 100, optional image seed; the 3D settings and seed apply to the second step) and then the 3D render chained to that picture. The picture is a normal image in the project library and the 3D asset's generation details point at it. The estimate on the page covers the 3D step only. Memory: the two models load one after the other, and Forge checks GPU and system memory before each and may unload an idle model to make room, so the second stage can include a model load. Before the 3D model is admitted, Forge frees Qwen Image when it can (see **Freeing the first model of a chain** under Automatic model management); an earlier run that kept both resident left the host short of RAM. MCP: `forge_queue_text_to_3d` (`projectId`, `prompt`, `model` `hunyuan` or `trellis`, `image` `{ steps, seed, width, height }`, `options` for the 3D model).

**TRELLIS.2 pipelines.** The 3D page's TRELLIS.2 **Pipeline** select (and `pipeline` over HTTP and MCP) offers `512` (default), `1024`, `1024_cascade` and `1536_cascade`. All of them use the checkpoints already in `models/TRELLIS.2-4B/ckpts` (the 1536 cascade reuses the 1024 models at a larger grid), so nothing needs downloading on this machine. Forge reads the checkpoint files to decide which pipelines to offer (also while the worker is stopped) and the worker re-checks; a missing checkpoint hides the option. The worker loads the two extra 1024 flow models (about 2.6 GB each, bf16) the first time a higher pipeline is used, not at startup, so the default 512 load is unchanged. Admission budgets (uncalibrated guesses, GPU memory is large and host memory is only a soft floor unless `FORGE_HOST_MEMORY_POLICY=strict`): 512 waits for 24 GB of free GPU memory and 12 GB of host memory as before; 1024 for 40 GB and 18 GB; 1024 cascade for 48 GB and 18 GB; 1536 cascade for 64 GB and 20 GB. The cascade lowers its own resolution when an object needs too many tokens. Timing history is kept per pipeline. All four were run on this Windows ARM64 stack on 2026-11-08 (measurements below); the GPU figures above remain cautious guesses, because the measured peaks were well under them.

**Hunyuan painter options (advanced).** With **Paint texture** on, **Painted views** (6 to 9) and **View size** (512 or 768 pixels) are available for experiments. The defaults are what the painter was trained on; in a test 8 views at 768 pixels looked no better, took about twice as long and used about 15 GB more GPU memory, and Forge waits for that much extra GPU memory before starting such a render. MCP: `texture_views`, `texture_view_size`.

**Export formats.** Open a 3D asset and choose **Convert**: GLB, glTF, OBJ, PLY and STL convert to any other of those formats. A copy is named `forge-<id>-converted.<ext>` (a number is added if the name is taken), the original is untouched, and the copy inherits the original's generation details. GLB to glTF and back repackages the container without changing the model (glTF is one text file with the data embedded). OBJ is saved with an `.mtl` material and the colour texture as a PNG beside it, all named after the copy (the PNG also appears in the Images list); metallic and roughness maps and animations are not part of OBJ. PLY has no textures, so the texture is baked into vertex colours (some detail is lost). STL keeps the shape only. Point clouds and Gaussian splats cannot be converted. Conversion runs `runtime/model_convert.py` with the Hunyuan3D environment's Python (trimesh); set `FORGE_MODEL_CONVERT_PYTHON` to use another. It is CPU file work and loads no model. The viewer opens GLB, glTF, FBX, PLY, OBJ and STL; an OBJ shows its shape without the `.mtl` texture. MCP: `forge_convert_asset` with `format` `glb`, `gltf`, `obj`, `ply` or `stl`.

**Not offered, and why.** Multi-view input needs the separate Hunyuan3D-2mv model, which is not installed (a download; its size has not been checked). Retexturing an existing mesh (both Hunyuan3D-Paint and TRELLIS.2 can do it upstream) needs a worker API for uploading a mesh and has not been built. TRELLIS.2's own background remover needs approved access, which is why SAM 3.1 does that job here.

**Request rules.** The queue accepts only the video settings listed above (plus the seed). Any other field, for example `fps`, is refused with a 400 that names it, instead of being dropped while a render of something else is queued; for `fps` the message says the engine is fixed at 24 fps. The MCP tool `forge_queue_video` refuses unknown arguments the same way. Jobs saved by earlier Forge versions, Rerun and Reuse settings only use accepted settings and keep working.

**GPU memory budget.** H3 Studio's own form always asks the renderer for 6 GiB of weights. Encoding a reference video needs more: with "use the sound of the reference videos" the render failed twice at 6 GiB ("cannot make enough memory ... need 9518 MB device / 9006 MB budget ... failed to encode MiniMax-H3 reference video 1") and passed at 12 GiB. When a video has reference clips and no budget was chosen, Forge sends 12 GiB, waits in the queue until that much GPU memory (plus the 2 GiB reserve) is free, shows "~12 GiB (reference clips)" in the page's budget line, and records 12 GiB in the generation details ("GPU budget set by Forge for reference clips"). A budget you choose is never changed, and it is also what the queue waits for. The figure is a measurement from one machine, not a guarantee, and the free-memory check is a snapshot rather than a reservation.

**Engine lifecycle.** The queue starts the video engine itself when a video job is waiting and the engine is not reachable ("Starting the H3 Studio worker."), the same way it starts the other engines, and it still waits until H3 reports its model files ready and no render running. It does not start one when `FORGE_VIDEO_URL` points the queue at a service started elsewhere (set `FORGE_AUTO_START_VIDEO=1` to allow it anyway); a separately started H3 is never managed or stopped by Forge. **Start connected services** starts every engine that is not on demand; the **Start service** button on a model's card, or `POST /api/runtime/engines/<id>/start`, starts one engine with the same ownership, port and recovery checks (an on-demand engine answers `on_demand` and is started through its own load operation). Starting a service never loads a model. **Stop service** (`POST /api/runtime/models/video/offload`) stops a video engine this runtime started: the guard refuses new requests, checks that nothing is in flight and that H3 reports no running render, and only then ends H3 and its renderer together. It answers "The engine has active or queued work." (and stops nothing) otherwise, and cannot stop an H3 started outside this runtime; use **Force stop…** (verified process identity) for a stuck one. An idle video engine holds no GPU memory, so Forge never stops it automatically to make room. A video engine started before this update has no stop operation until it is restarted once.

**Failed renders.** H3 reports a failed render only as "engine exit N". Forge says "The video engine crashed (0xC0000409), often under memory pressure. Retry; if it repeats, offload other models and lower max GPU memory/size." for exit 3221226505, and names the GPU memory budget when a reference did not fit. These are H3's own final answers, so **Retry** submits a fresh attempt; Forge never resubmits by itself.

Everything above is covered by unit tests of the validation, the launcher's argument rewriting (against a substitute H3 server), media preparation (real decoding of generated clips) and MP4/GIF conversion. Real-engine checks on 2026-11-08 (one render at a time, on the H3 engine started with the guarded launcher; the Ref2VA checkpoint only): reference images, a reference video with a reference audio clip, "Also save an MP4" (H.264 with AAC, recorded as a conversion of the WebM), the converter to MP4 and GIF, Medium, 21:9, 243 and 311 frames (311 frames took about 9 minutes), the turbo adapter (all 624 LoRA tensors applied), guidance 2 with a negative prompt, and the sampler, scheduler, 10 GiB budget and reference detail max settings all completed. ### Newly exposed engine options (images, music, sounds, voices, speech)

These controls connect abilities the engines already had. They are covered by request, worker-protocol and interface tests with substitute engines. The image options were also rendered on the real engine on 2026-11-08 (below); the music, sound and voice options carry their own verification notes, and audio quality was not judged by ear.

**Images (Qwen Image 2.1), Fine-tune image.**

Verified through the studio UI and MCP on 2026-11-08 with the real Qwen Image Studio (BF16, patched `app.py`, `peft` 0.21.2, diffusers 0.42.1; images judged by a quick look only, not a quality review): a cold first 1024 × 576, 30 step render took 121 seconds (about 79 seconds loading) and a warm one 27 seconds; the same prompt, seed and settings repeated bit for bit. Three variations with seed 100 gave seeds 100, 101 and 102 (a blank seed gave three distinct random seeds), each with different output, and `variations` through MCP behaved the same. The camera-angle LoRA loaded, changed the image at strength 0.8 and 1.0, repeated bit for bit, and the next render without it matched the earlier one bit for bit, so it is unloaded after each job. Turning the KV cache off made a 12 step reference edit about 55 percent slower (42 s against 27 s) and gave a different image; a reference size target of 512 gave a 512 × 512 result in 6 seconds; a custom schedule of four sigmas ran 4 steps; the transparent option returned a PNG with real alpha. A 1536 × 1536, 8 step render peaked near 49 GB of GPU memory for Qwen (the admission estimate for that size is about 57 GB, so it is conservative). A 2752 × 2752 request with the model loaded and 52 GB free correctly waited for GPU memory (needs about 78 GiB) and was cancelled before it started.

- **Variations** (1 to 4) queues that many sibling renders with the same settings and different recorded seeds (a seed you enter is used for the first and counted up from there). The queue and Generation details label them "variation 2 of 4"; Reuse settings and Rerun make a single render. The engine's own `num_images_per_prompt` is not used because a Forge job holds one output. MCP: `variations` on `forge_queue_image`.
- **LoRA** and **LoRA strength** (0 to 2). Forge lists the `.safetensors` files in `models/Qwen-Image-2.1-LoRA` (`forge_image_loras`, `GET /api/runtime/image-loras`); only a listed file name is accepted, never a path. `QwenImage21Pipeline` inherits diffusers' LoRA loader, but the stock Qwen Image Studio app did not call it and its `.venv` lacks the `peft` package. The patch is recorded in [MODEL_SOURCES.md](MODEL_SOURCES.md); install `peft` into that `.venv` and restart the app. Until then a LoRA job fails before submission with an explanation (Forge asks the engine's `/api/loras` first, because an unpatched app would silently ignore the field). A LoRA must be trained for Qwen Image 2.1. The camera-angle file `angles_v2_step1500.safetensors` (ai-toolkit, `qwen_image_2`) loads and changes the output. Its fused `img_mlp.gate_up` weights (64 of its 384 tensors) used to be skipped, because the 2.1 transformer's MLP has separate `proj` and `gate_layer` layers. Qwen Image Studio now splits them into those two layers when loading (`QWEN_LORA_GATE_UP_ORDER`, default `gate_first`), so all 384 tensors load with no unexpected keys in the engine log. Both halves orders gave clean images for front, back and high-angle prompts; `gate_first` was kept because the two looked alike by eye. That judgement is not an objective angle-accuracy measurement, and the test prompts were text-to-image, while the card describes image-to-image use with a reference photo. The LoRA also changes the subject's colour and shape, not only its angle.
- **Advanced: KV cache** (on by default). It reuses prompt and reference computations on every step, which speeds up edits with references. Turning it off gives a different but equally valid image for the same seed, so it is a comparison tool, not a quality control.
- **Reference size target** (256 to 2048 px) with "Match the last reference's shape": the pixel side length the matched size is built around (default 1024, about one megapixel). Above about 1536 needs far more GPU memory.
- **Advanced: custom sampling schedule**: a comma-separated list of falling sigmas (for example `1, 0.8, 0.5, 0.2`); its length replaces Sampling steps. Qwen Image has one scheduler (flow-matching Euler with dynamic shifting) and its API accepts sigmas, not a scheduler class, so a scheduler list is not offered. Schedules are stored as text, so very long ones are shortened in Generation details.

**Music (YuE2).** On any music file Forge rendered, **Extend this track** (1 to 300 seconds, optional new lyrics for the added part) and **Re-synthesize with a new seed** (optional synthesis steps) appear in Recent creations and in the asset library. YuE2 keeps each track's planned song tokens, so the request names the project file and the queue resolves it to the finished YuE2 render that made it (`POST /api/jobs/extend` and `/api/jobs/resynth` on the engine); no audio is uploaded. The original track is not changed and the new file records the original as its parent. Only tracks Forge rendered and YuE2 still has can be used (a file imported by hand cannot). MCP: `forge_extend_music`, `forge_resynth_music`. Extending re-renders the whole track, so its time grows with the combined length. Verified through the studio UI on 2026-11-08 (real YuE2 renders, judged by metadata only, not by listening): a 15 second track took 67 seconds; extending it by 12 seconds gave a 27.0 second FLAC in 18 seconds, extending that result by 10 seconds gave 37.0 seconds, and re-synthesizing the 15 second track took 9 seconds and gave a different 15.0 second file. The original files were unchanged, and extending a track rendered with Planning off also worked. A rerun of an extension repeats it with a new seed; the style cannot be edited because it comes from the source track.

**Sound effects (Stable Audio 3).** **Start from an existing sound** (in Fine-tune sound) picks a WAV, FLAC, MP3 or Ogg file of up to 32 MiB from a project; Forge copies it when chosen. Then choose **Variation** (audio-to-audio; **Change amount** 0.05 to 1, default 0.9, lower stays closer to the source), **Replace a part** (start and end seconds, inside the duration) or **Continue** (keeps the source and generates the rest up to a longer duration). The Lab's `/api/generate` gained `source_audio` (base64), `edit_mode`, `init_noise_level`, `inpaint_start` and `inpaint_end`; the patch is in [MODEL_SOURCES.md](MODEL_SOURCES.md). Forge checks the Lab's `audio_input` status flag before submitting, so an unpatched Lab fails the job with an explanation instead of ignoring the source. The post-trained Medium model still ignores negative prompts and guidance, and looping is not connected. MCP: `forge_stage_audio_source` then `forge_queue_sound` with `source_audio` and `edit_mode`.

**Voices (Qwen3-TTS).** Fine-tune voice adds a **Sampling mode** (sample or greedy) and a **Fine detail (sub-talker)** group: sampling switch, temperature (0.05 to 2, model default 0.9), top-p (default 1) and top-k (default 50) for the second-stage model that fills in each speech frame's acoustic detail. Blank values keep the model defaults. Greedy makes temperature, top-p and top-k irrelevant. The worker change takes effect when the speech worker next starts. The upstream library notes the sub-talker options apply to its v2 speech tokenizer; on the installed tokenizer, changing the fine-detail temperature or switching its sampling to greedy changed the rendered audio (checked on 2026-11-08 with a fixed seed), so those options are honoured; top-p and top-k were not tested separately. Voice cloning (`Qwen3-TTS-12Hz-1.7B-Base`, about 4.5 GB) and voice design (`Qwen3-TTS-12Hz-1.7B-VoiceDesign`, about 4.5 GB) need other checkpoints; they are optional staged downloads (`.\install.ps1 -Models tts-base,tts-voicedesign`, never part of `-Models all`) with their revisions and checksums in [MODEL_SOURCES.md](MODEL_SOURCES.md). The Voices page's clone and design modes use them. Their memory budget is an uncalibrated 8 GiB working budget plus the same 2 GiB reserve, and a checkpoint switch is admitted only when free GPU memory covers that budget, since the resident checkpoint is not counted as freed. A worker started before this change must be restarted before clone or design can load; a voice-only clone sent to an older worker is refused for a missing transcript, which is the signal to restart it.

**Speech recognition (Nemotron).** Voices, Recognition options, **Latency** chooses the streaming chunk: 80, 160 (default), 560 or 1120 ms, which are the model's cache-aware right contexts 0, 1, 6 and 13 (`--asr.streaming.rnnt_right_context`). The engine reads it only at startup, so applying a change saves it and, when Forge owns a running idle speech engine, stops and starts it again through the normal memory-checked start. While a transcription session is connected the engine refuses to stop; the choice is kept and applies at its next start. The control is disabled while recording or transcribing. The value is stored in `.forge-runtime/asr-latency.json`. MCP: `forge_asr_latency`, `forge_set_asr_latency`. Whether the 80 and 1120 ms modes change recognition accuracy as NVIDIA describes has not been measured here.

### Generation details (model and prompt for every asset)

Every file Forge creates records how it was made so you can reuse it later: the **model** (name, id, and checkpoint folder), the **prompt** (plus negative prompt, lyrics or voice direction, and title where the model has them), all **settings** (seed, steps, size, duration, texture options and so on), the **reference images** it used (staged file names and sizes only, never the image bytes), timing, the render id, and, for converted copies, the file it was converted from. Open an asset in the library, or look under **Recent creations**, and read **Generation details**. **Copy prompt** copies the full prompt. **Reuse settings** opens the matching creation page with the model, prompt, and options filled in; reference files cannot be re-attached automatically, so choose them again. Worlds open the World page with the generator, starting point, prompt, output, size, seed, steps and advanced options filled in; choose the reference images again.

The library search box matches names, prompt text, and model names, and a **Model** filter appears once any asset has details. List and grid cards show the model.

**Where it lives.** One SQLite database per project, `<project>/.forge-meta.sqlite`, next to `.forge-project.json`. It is hidden from the asset list, uses a single file (no `-wal` or `-shm` companions), and has indexes for model, render id, and date plus an FTS5 text index for prompt search (with a plain `LIKE` fallback). Because it sits inside the project folder it is backed up, copied, and moved with the project, and any SQLite tool can query the `asset_meta` table. Rows are keyed by the project-relative asset path; renaming moves the row, trash and restore keep it, and clearing the trash deletes it. The schema version is stored in `PRAGMA user_version` (currently 1) and migrations run automatically. A database written by a newer Forge is left untouched and not used. A damaged database is renamed to `.forge-meta.corrupt-<time>.sqlite` and replaced by a fresh one; recording details never fails a render or hides your assets.

**What is saved.** Details are written when a render is saved to the project, when a converted copy is made, and when a chat reply, transcript, or game decision is saved to a project. Fields are length-limited (prompts up to 20,000 characters), secret-looking text such as API keys or bearer tokens is redacted, and API keys, endpoints, environment variables, and absolute file paths are never stored. Prompts are stored in plain text in your project folder, so exclude `.forge-meta.sqlite` if you share a project and the prompts are private.

**Older assets.** Files created before this feature are filled in the first time they are viewed: Forge matches the `forge-<render id>` file name (or the original name of a renamed file) to the render history in `.forge-runtime/jobs.sqlite`, which it only reads, and saves the result as a recovered record. Converted copies inherit the details of the file they came from. Files whose render is no longer in the queue history, and files you added yourself, show "No generation details recorded for this file."

### Visual asset thumbnails

The library, project covers, and recent-creation strips create thumbnails as visual assets come into view. Forge takes an image or video frame, renders supported 3D models, or captures the first skeleton pose for BVH motion. Project thumbnails are cached under the project's hidden `.forge-thumbnails` folder and regenerated when the source file changes. Opening an asset still uses the full image, video, or interactive 3D/motion viewer. The thumbnail renderer limits model files to 64 MiB and only loads embedded model resources; a file that cannot be decoded or uses external resources shows a preview-unavailable placeholder.

Use **Full screen** on a 3D or motion preview in the library or a recent-creation panel to inspect it in a larger modal. Drag to rotate, use the on-screen controls to rotate or zoom, and pause or play motion. Close the modal with **Close** or Escape to return to the same asset.

## Recovery after a crash or power loss

Forge is built to survive the studio, a worker, an engine or the whole computer stopping suddenly. The queue is a SQLite database written with full synchronous flushes; every file a render saves is written under a hidden name, flushed, and only then given its real name, so a power cut cannot leave a half-written asset behind. Engines keep running when the studio stops, and Forge reconnects to them when it can prove it started them.

When the studio starts after a stop that was not an orderly shutdown (crash, `Stop-Process`, power loss, a Windows shutdown that did not finish in time), or after a database was repaired, a **Recovery** panel appears under the top bar. It says when the studio was last running and lists what needs a decision:

- **Renders whose outcome is unknown.** A render that may have reached an engine before the interruption is never run again automatically. Check the engine (Models & services); if a saved output is listed it is already in the project. After you tick _I checked that the engine is not rendering this job_, **Mark as cancelled** closes it. **Queue again** is shown only for a render that provably never reached an engine.
- **Files left by an interrupted operation.** Stale temporary files older than 24 hours are removed at start. Anything else is listed by project and project-relative path, and **Move to quarantine** puts it in `.forge-runtime/quarantine/` (nothing is deleted).
- **Databases.** A database that failed its integrity check is set aside as `<name>.corrupt-<time>`, the newest backup is restored, and the panel says how old that backup was. Backups are made every 15 minutes in `.forge-runtime/backups/`.
- **Engines** that are not responding, told apart as _not running_ and _not answering_, and whether Forge re-adopted the ones that survived.
- **A process that kept crashing.** After five crashes in ten minutes the studio host or runtime worker is not restarted again, and the studio address shows a _Recovery needed_ page until you fix the cause and start the studio again.

**Dismiss** hides the report until something new needs attention. The same report is available at `/api/recovery` and through the `forge_recovery_report` MCP tool. Closing the browser window does not stop the studio; **Stop Studio...** in the tray (or `stop-server.ps1`) asks the studio to stop in an orderly way first and terminates it only if it has not exited after eight seconds. The details, the guarantees and non-guarantees, and the manual crash drills are in [Resilience](RESILIENCE.md).

## Troubleshooting

**The page will not open.** Run the start script again, check the address it prints, and inspect the log path it reports. Make sure Node.js is available and run `npm install` if dependencies are missing.

**The port is in use.** Start on a different port with `-Port 5199` and open the printed address. Use the same port when stopping the server. A different port has separate browser-local settings.

**A music job is waiting for its engine.** Forge starts YuE2 and requests the model automatically. Check Diagnostics if startup or loading fails. If GPU memory is insufficient, use the memory dialog to offload an eligible idle model or free memory externally, then retry.

**A job is interrupted.** Check the relevant engine's own queue and history for the corresponding render before resolving the item in Forge. An interrupted job blocks later jobs so an uncertain submission is not silently duplicated.

**An asset does not appear.** Check that it is inside a project folder and uses one of the indexed formats listed above. Allow a few seconds for the project listing to refresh.

**Notifications do not appear.** On Windows, open the Forge tray icon and use **Test Windows notification**; check Windows notification settings and Focus. For browser alerts, check browser permission and keep the Studio page open.

**A model cannot be deleted from the UI.** Check that it is in Forge-managed storage, its service is stopped, and no custom endpoint or filesystem links prevent removal. Models stored in other applications must be managed there.

**A console or Windows Terminal window flashes open.** Forge starts engines hidden and gives them a hidden console, so none should appear (see [how engines are launched](WINDOWS_ARM64.md#how-engines-are-launched-on-windows-no-console-windows)). If one does, note the time and use `Get-CimInstance Win32_Process` to see which program is the parent of the new `cmd.exe`, `conhost.exe`, or `powershell.exe`; windows opened by other applications are outside Forge's control.

**You need help debugging.** Open Diagnostics, copy the relevant logs and server metadata, and include what you clicked and the time of the issue. Check logs for private content before sharing.

## Chat and Qwen3.8

The Chat workspace supports streamed conversations, project-scoped browser history, text/JSON/JSON-schema responses, and OpenAI-compatible servers. Configure an OpenAI API key in the panel for the current page session, or set `OPENAI_API_KEY` in the studio server environment. The key is not saved with chat history. ChatGPT/Codex sign-in is not currently connected; this integration uses the API key route. Conversations are browser-local, not files in project folders.

Sending a message to the default local Qwen alias starts its managed GPU server on demand if it is not already running. The message remains in the composer during startup and is sent when the server is ready. If memory is insufficient, select an eligible idle Forge-managed service in the memory dialog or cancel and keep the unsent message. Other compatible endpoints are never started by this flow.

The local Qwen button uses the existing file `models\Qwen3.8-27B-GGUF\Qwen3.8-27B-Q4_K_M.gguf`; LM Studio is not the inference server. The installed GGUF metadata includes one next-token prediction layer. Forge starts the official native Windows ARM64 CUDA llama.cpp server with `--device CUDA0 --n-gpu-layers all --fit off --ctx-size <selected> --parallel 1 --spec-type draft-mtp --spec-draft-n-max 3`. This config requests MTP speculation; confirm activation and performance in `.forge-runtime/engine-chat.log` after a successful model load. Forge reserves the render queue while starting and checks an estimated system and GPU memory budget that grows with the selected context size; at 4K, the admission threshold is 21 GiB of free GPU memory, including a 2 GiB GPU reserve. System RAM is not part of this check for the all-GPU GGUF engine; Windows commit and RAM pressure can still fail a start, and the engine log reports that. These are snapshots, not reservations. The estimated 18.75 GiB total at 4K came from LM Studio's offline resource estimator. The bundled `llama-fit-params` reports a 405 MiB FP16 context allocation at 4K and about 64 MiB more for each additional 1,024 tokens; the on-screen total also allows for a small increase in compute memory. Actual use, including speculative decoding overhead, is not yet calibrated. The selected context applies on the next start; prompt, history, reasoning, and output share that limit. Maximum output tokens is a per-request cap and can be smaller than the context. The Force stop control applies only to a process whose ownership Forge can verify. An uncertain load or an unowned service may need review before the queue continues.

The native runtime is the official [llama.cpp b12180 release](https://github.com/ggml-org/llama.cpp/releases/tag/b12180), downloaded as `llama-b12180-bin-win-cuda-13.5-arm64.zip` (SHA-256 `86953cf12dd867676b387f2d319a2bfff918065163a5e48bda3a463c64f47d76`) and `cudart-llama-bin-win-cuda-13.5-arm64.zip` (SHA-256 `f89e7b2457f627d052dd99f42205ddfd01964454809754cdc649cffc74320dca`). Both archives were verified against the release's published digests before extraction. The [Qwen3.8 GGUF source](https://huggingface.co/lmstudio-community/Qwen3.8-27B-GGUF) remains in the existing model library and was not duplicated.

A compatible server such as vLLM can be connected over localhost or a private IPv4 network. [vLLM documents Linux as its supported platform](https://docs.vllm.ai/en/stable/getting_started/installation/gpu/); Forge does not use WSL or start vLLM on Windows. For external servers, GPU offload, model loading, speculative decoding, and render-queue coordination are configured and verified on that server, not by Forge.

Chat response controls are beside the message box: text, JSON object, or a strict JSON schema, plus model-default/off/low/medium/high thinking. For the Forge-managed local server, low/medium/high request thinking budgets of 256/768/1536 tokens; actual behavior depends on the model and server. The speculative-decoding switch applies to the next local Qwen start and requires stopping an already-running instance first. Other compatible servers control their own decoding settings and may not implement these fields. **Advanced sampling** (Advanced settings) adds top-p, top-k, min-p, presence and frequency penalties, seed and up to four stop sequences. Blank fields keep the server default. Values are checked at the Forge boundary, the same checks apply to the `forge_chat` MCP tool, and top-k and min-p are refused for OpenAI. The local engine's thinking switch, when set to Off, sends `enable_thinking: false` to the chat template; a live run on 2026-11-08 showed no reasoning output with Off (with or without the explicit flag), while the default setting produced reasoning. **Thinking High on the local engine** is sent to the Qwen3.8 template as `reasoning_effort: "xhigh"`; the template rejects a plain `high` with an HTTP 500 (seen on llama.cpp b12180 on 2026-11-08). Other servers still receive `high`. The `xhigh` mapping is covered by a unit test and a direct llama.cpp check; it was not exercised through a restarted studio.

**Image input (vision).** When `models/Qwen3.8-27B-GGUF/mmproj-Qwen3.8-27B-BF16.gguf` (about 0.93 GB) exists, Forge starts the local Qwen server with `--mmproj <file> --image-max-tokens <n>` (n is the smaller of 2,048 and a quarter of the context, so one picture cannot fill a small window). Without the file the server starts text-only and Chat says `Vision files missing`. Whether pictures work is read from the running server's `/props` (`modalities.vision`), never assumed from the file: a server that was started without the projector keeps refusing pictures until it is force-stopped and started again. The estimated GPU budget and the start-time memory check add about 0.93 GiB (950 MiB) when the projector is used; this is an estimate. **Attach image** (file picker, paste or drag and drop) and **From project** (the asset picker) accept PNG, JPEG or WebP, up to 4 per message and 8 MiB each (20 MiB in total) after shrinking. The type is read from the file's first bytes, not its name. The browser shrinks pictures to at most 1,536 px on the long edge before sending; JPEG pictures are always re-encoded, which applies their rotation and removes their metadata. Pictures go only to the local Qwen engine (port 8098); OpenAI and other compatible servers are refused. The control is disabled with a reason when the connection is not the local engine or the server has no projector. Pictures are sent with the message they are attached to; later turns see only the text and the answer, and each picture costs up to the `--image-max-tokens` share of the context window. Saved browser history keeps only a 96 px thumbnail and the project asset reference (never the picture data). The `forge_chat` MCP tool accepts `projectId` plus up to four project image paths in `images`, attached to the last user message with the same checks. A live run on 2026-11-08 (4K context, speculative decoding on) loaded the projector (`loaded multimodal model` in the engine log, `/props` reporting vision true) and answered a question about a project apple render correctly; see the Chat tests in test/README.md for what is covered by automated tests. Picture answer quality was only spot-checked.

The render queue appears in the asset library and creation panels. “Hide current rows” only hides the current job IDs in this browser; it never stops work and can be undone with “Show hidden.” “Clear waiting renders” requires typing CLEAR and cancels eligible queued/waiting jobs across projects. Running jobs, jobs with a remote ID, and uncertain jobs are left alone; completed assets and job records are kept.
